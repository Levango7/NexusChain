## 2. 时长与成本口径

- **单次全跑时长**【实测锚点】：S2 本机实测约 **18–20 min**（收敛 4min + 基线 1min + 分区 2min + 治愈 2min + 证据）；S1/S4/S5 各约 30min、S3 约 40min【估算】⇒ **一次全跑 ≈ 2h 量级**，按需计费即 2 机时/次。
- **成本**：【询价】。可先用**按量/竞价实例**跑一轮定性，再决定是否保留常驻。
- **能省的成本点**：镜像可用 CI 已推的 GHCR 制品（`v2.72.0` 起 13 镜像齐备【实测，见 `install-rehearsal-resources.md`】）⇒ 云主机不必现构建（省 3–4GB 内存与 20+ min）。

## 3. 拿到环境后的执行路径（现状与缺口，别当成"一条命令"）

- ✅ **单内核形态已有可跑资产**：`scripts/drill/a1-wsl-partition-drill.sh`（`A1_REPO`/`A1_PGUSER`/`A1_PGPASS`/`A1_WORK` 可覆盖；
  判据与证据格式已固化；2026-11-16 两次干净复现）。
- ⚠️ **跨机形态尚无现成脚本**：该脚本用「单机多 UID + `-m owner --uid-owner`」切流；
  跨机需改为**按对端 IP/端口**的 DROP 规则 + 逐机 SSH 编排 —— 这一层尚未入库，
  属**拿到环境后的第一件活**（可参照 `scripts/drill/drill-common.sh` 的 Tier-2 约定：
  `DRILL_NODE_HOST_A/B/C` + `DRILL_EVIDENCE_ROOT`）。
- 建议顺序：**S5（取证最便宜）→ S1 → S2 → S4 → S3**。

## 4. 本机 kind 集群（`nc-alert-drill`）的择时拆除

- **现状**：B-11 演练集群仍在跑（`nc-alert-drill-control-plane` 等）；**按本页决策=择时拆除**，
  但**拆除前请确认**没有其它线在用该集群做复验（板面/留言确认）。
- **拆除路径（幂等）**：`docs/runbooks/kind-alert-drill.md` 的 `down` 子命令；拆后核残留：
  `docker ps | grep nc-alert-drill`（应无）、`kind get clusters`（应无 `nc-alert-drill`）。
- **拆除不损失结论**：B-11 的三层证据（Prometheus firing → AM active receivers → sink 200 回执）
  与 10 类环境坑已固化在 runbook 与板面通告里【实测，2026-11-14 交付】。

## 5. 边界（勿夸大）

- 本文只是**申请单 + 执行路径**，**不构成资源承诺或预算批准**；规格为下界【估算】；
- 托管 K8s 与自建 K8s 在 **网络插件/存储类/节点运维**上不同，
  B-11 复跑时要按 runbook 的坑清单逐项对一遍（尤其 webhook TLS 与 ServiceMonitor 标签口径）；
- 跨机分区脚本**尚未入库**（见 §3），别把"环境到位"当"可立即全跑"；
- 生产库执行（A-8/A-9）与完整红队（B-13）**不在本文范围**。
