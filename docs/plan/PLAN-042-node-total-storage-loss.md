# 方案 PLAN-042：节点全量持久化丢失后的自愈实证（roadmap #30「磁盘损坏/数据丢失」）

- **状态**：已交付（2026-10-26）；本机两进程实证，预登记五判据全过
- **性质**：验证切片——**产品代码预期零改动**；若有 bug 落盘，另行修复切片
- **前置**：PLAN-041（晚加入/冷启动自愈已证）、PLAN-020（重启追平）、PLAN-033
  （大缺口追块加速）、PLAN-021/025（最终性视图收敛与补票）、PLAN-030（验证人集
  全表回放）、#195（outbox 恢复上限与 fail-closed）
- **对应 roadmap**：#30「仍未做」里的"磁盘损坏"、#27「数据库整体不可用时只剩内存
  队列兜底 / 补票窗口外远古 epoch 不补」的更强形态——**全量丢失**（不只是 PG 停机）。

---

## 一、问题与假设

#30/#27 已覆盖的边界：
- PG **停机**（节点进程活着，内存链继续）——PLAN-017/018/019/#195/PLAN-039；
- 进程**重启**（持久化完好、数据未损）——PLAN-020；
- 单节点 **冷加入**（从空库启动、 peers 在跑）——PLAN-041。

未覆盖的形态：**节点持久化全损**（模拟磁盘损坏/数据丢失）：PG 库整个没了、
本地 LevelDB 缓存也没了，**只留进程**。此时该节点是否能在不人工干预种子的前提下：
重新认人（验证人集）、重新追块、重建最终性、并重新参与出块？

**假设（待证伪）**：上述四项中有一项做不到 ⇒ 需要修复切片；
若四项都做到，则把 #30 的"磁盘损坏"条目标记为「本机边界已证」（如实标注不覆盖物
理磁盘损坏/多机）。

## 二、实验设计（预登记判据）

拓扑（同 PLAN-041 的 Windows 两进程 + 两个独立 PG 库，如实边界见 §五）：

| 节点 | 角色 | 存储 |
|---|---|---|
| A | 常驻 mining | PG 库 `nexuschain`（全实验**不动**） |
| D | 正常加入后**全量丢失存储** | PG 库 `nexuschain_d` + LevelDB `data-d` |

流程：
1. A 启动出块到 height ≥ 60；
2. D **正常**启动（空库）并收敛（与 PLAN-041 同构）；
3. 到达 ~height 500 后（A、D 均在出块、最终性在走） T0：停 D →
   **DROP DATABASE `nexuschain_d` 重建空库 + 删除 `data-d` 整个目录**；
   以**完全相同的启动参数**重启 D（模拟"磁盘坏了、运维重装同一台机器"）；
4. 采样 15×20s：A/D 高度、D `unknown proposer` 累计、D `validators_synced` 行数、
   A/D 两侧 `finality_checkpoints` 计数与最大高度、D 日志中 **D 自己地址的
   出块/广播/投票**事件。

**预登记判定**（先定标准后跑）：

1. D 重新自注册（日志 `Self-registered`）并经回放拿到 A 的集合
   （`validators_synced` ≥2 行，含 A 与 D 自身）；
2. D 高度越过 1 并收敛到 A 附近（追块单调不回退；用 accelerate 补大缺口）；
3. D 日志 `unknown proposer` 计数**有限且最终不再增长**；
4. D 重新参与出块与投票（出现 D 地址的提议/广播/最终性投票事件；两侧
   `finality_checkpoints` 存在且持续增长）；
5. A 全程高度单调增、不停摆（对照侧不得掉）。

## 三、结果（2026-10-26，一次跑成；判据全过）

| 采样（T0=05:27:04 销毁存储 → 05:27:09 同参重启） | A | D | D `unknown proposer` |
|---|---|---|---|
| 销毁前基线 | 303 | 304 | 0 |
| t+20s | 313 | 0（启动中） | 1 |
| t+40s | 319 | 0 | 1 |
| t+60s | 325 | **256**（一次补 ~250 块） | 1 |
| t+80s | 343 | 344 | 1 |
| t+100s…t+300s | 391…848 | 391…849 | **1（不再增长）** |

**判据逐条**：

1. ✅ **重新认人**：重启 20s 内自注册（`Self-registered ... address=aKURTTsKzhtB8itmyDbzC9ixRFPSUANv9`），
   T0+50s 经对端全表回放拿到 A（`Validator-set add: address=nv3gC5mGzFjtv2ouzw3Yd3vQYbfys3tD8 registered=true (via P2P)`）；
   D 库 `validators_synced` = **2 行**（A + D 自身，与 A 库相同）。
2. ✅ **追块收敛**：T0+51s 高度 0→256 一次补落库（大缺口走 PLAN-033 加速窗口），
   之后逐块跟随，最终 A=**848** / D=**849**（stop 采样差 1 块内）。
3. ✅ **`unknown proposer` 可恢复**：全程 **1 次**（出现在启动初期，之后计数不动）。
4. ✅ **重新出块 + 重新投票**：`PosProposer Selected proposer aKURTTsKzhtB8itmyDbzC9ixRFPSUANv9 at height 328/330 (ordered set size=2)`（回到轮转）
   + D 地址的最终性投票持续广播（`Finality vote submitted ... finalized=true, progress=100%`，epoch 420→426）；
   库级证据：D 从空库重建出 **375 个检查点 / 752 票**（A 侧 426 个 / 852 票）
   ——D 丢失的远古部分由 PLAN-025 的 vote-sync 补回（D 日志：
   `Vote-sync request (from epoch 373) served with 102 votes`），重建区间
   375..426 与 `426-375=51` 个 epoch 缺口对应一致。
5. ✅ **A 全程不中断**：高度 303→848 单调增、无停摆（对照侧）。

## 四、结论与处置

- **#30「磁盘损坏/数据丢失」在本机边界已证**：节点**全量持久化丢失**（PG 库没了 +
  LevelDB 缓存没了）后，不人工种子的前提下：重新自注册 → 全表回放认 A → 加速追块
  0→256 → 回到 proposer 轮转与投票 → 检查点经 vote-sync 重建 375/426 → 与 A 收敛。
  产品代码零改动（机制组合：PLAN-030 回放 + PLAN-033 追块 + PLAN-028 view-change
  + PLAN-021/025 最终性补票）。
- `docs/roadmap-unresolved.md` #30 行更新 + 治理记录；CHANGELOG 摘要。
- **一处如实登记的不确定**：测量窗口末点，A 侧本地最终性视图
  `progress=50% / finalized=false`（epoch 422-426），D 侧同时 `progress=100%`。
  两者对 checkpoint hash 完全一致（每 epoch 同串），差别在**本地聚合进度**——
  2 验证人拓扑 + D 刚冷恢复的组合下未做长窗口收敛观测。不作为缺陷宣布，
  登记为后续测量项（多验证人/更长窗口）。

## 五、边界（勿夸大）

1. **本机同内核两进程** + 两个独立 PG；不含物理磁盘损坏、跨内核/物理多机、网络
   分区、断电；"全量丢失"用 **DROP DATABASE + 删缓存目录**模拟，不是块设备故障；
2. 补票窗口回看 50 epoch（PLAN-025 默认）：T0 之前的远古检查点**不会**从网络补回
   （如实登记，#27 同名边界不变）；
3. A 的注册表内**保留 D**（D 早先自注册过、落库在 A 侧）——若配合真实场景（A 也
   新装），由 PLAN-030 回放同样覆盖；
4. `min-validators-to-mine=2` 是集群既有默认；D 拿到集合前不会单独开分叉。
