# 方案 PLAN-048b：补票回看窗 margin-epochs 的产品决策测量（默认 50 → 200？）

- **状态**：已交付（2026-10-27）；margin=200 单次实测，结论明确
- **前置**：PLAN-047（干净基线下 E 宕机 105 epoch ⇒ 补回 76、**永久丢失 29**，
  与 margin-epochs=50 的定性边界吻合）+ PLAN-025（回看窗实现）
- **范围**：**只测不改默认值**——用 `margin-epochs=200` 复跑同一场景，
  量化"窗外缺口是否清零、代价是什么"，产出产品决策建议（默认值调整/
  保持 + revisit 条件）
- **不包含**：改默认值、改 anti-entropy 算法、性能压测

---

## 一、问题

PLAN-047 Run 2 给出一次数据点：margin=50、宕机 105 epoch ⇒ 丢 29。
但"丢 29"是**窗口不够**还是** Peer 侧也没有更早的票**？Peer（A/D）库里存着
全部历史票（`finality_votes` 只增不减），因此若把 margin 提到 200，
理论上 105 epoch 的缺口应能全部补回——**这决定了产品默认值是否要从 50 上调**。

代价侧未知：margin 越大，单次 `Vote-sync` 响应要带的票越多
（当前上限 `max-votes=200`），可能拆成多轮；对网络/存储的压力需要量化。

## 二、实验（预登记判据）

与 PLAN-047 Run 2 完全同构，唯一变量 `--nexus.finality.anti-entropy.margin-epochs=200`
（三节点同参）：

1. E 宕机 631s（~105 epoch）后重启，统计 E 最终检查点数与 A 的差
   （**期望：差 ≈ 0**，即窗外缺口清零）；
2. 统计补票轮次/每次 `served with N votes` 的分布（**代价量化**：
   200 epoch × 3 验证人 ≈ 600 票 > max-votes 200 ⇒ 预期 3+ 轮）；
3. 若缺口清零且代价可接受 ⇒ 建议默认 50→200（或按 SLA 取中间值）；
   若缺口不清零 ⇒ 结论是"peer 侧/协议侧另有限制"，转查。

## 三、结果（2026-10-27；margin=200，其余同 PLAN-047 Run 2）

**P3 E 重启（40×15s）——判据 1/2 双双达成**：

| 指标 | margin=50（PLAN-047） | margin=200（本跑） |
|---|---|---|
| E 追块启动 | +15s 已从 113 追到 226 | +45s 已恢复到 h=332/164ckpt（启动略慢，首批要搬的票多） |
| 终态检查点 | A=363 / E=334（**缺 29**） | **A=272 / D=272 / E=272（缺 0）** |
| 宕机 ~105 epoch 的补回率 | 76/105 | **105/105（全补回）** |
| `served with N votes` 分布 | 99~152 | **持续 200（打满 max-votes 上限）** |
| 补票请求节奏 | from epoch 305 起（贴近窗口尾） | from epoch 65 → 72 逐轮推进（分多轮搬完全部） |

**判据 3（代价）**：margin=200 时单次响应**打满** `max-votes=200` 上限
（投票对象 ~600+ 条 > 上限 ⇒ 拆成多轮，约 10+ 轮搬完），每轮 5s 一个请求，
**总耗时 ~2 分钟内完成**；网络/存储压力表现为"多轮小批量"而非"单次大包"——
这是 `max-votes` 上限的设计意图在起作用，代价可接受。

## 四、结论与处置

**结论：margin-epochs 从 50 提到 200 可把"窗外永久丢失"清零（本例 29→0），
代价是补票拆成多轮但总时长仍在分钟级。**

**产品决策建议（本切片只建议，不改默认值）**：
1. 若 SLA 允许宕机 ≤2 小时（~1200 epoch 之外的更长窗口另议），margin 取
   **宕机时长 × epoch 速率 + 余量**——本拓扑 6s/epoch，105 epoch≈10.5 分钟；
   margin=200 覆盖 ~20 分钟宕机仍有 2× 余量；
2. **不建议无上限调大**：margin 越大，恢复时 `from` 越早、单次要搬的票越多，
   会在 `max-votes` 上限前拆成更多轮；真正的下限约束是"恢复总时长"而非
   "margin 值"；
3. **revisit 条件**：① 若实测更长宕机（如 1 小时）仍丢 epoch ⇒ 需要
   "分页续传"（游标式）而非单纯调大 margin；② `max-votes=200` 若成为
   恢复时长瓶颈 ⇒ 评估上调 max-votes 与单次响应体积的权衡。

**默认值处置**：维持 50 不动（改默认值属产品决策 + 需要运维 SLA 输入），
本切片把"50 够不够、200 的代价"量化成可引用数据；roadmap 对应行更新。

## 五、边界（勿夸大）

- 单次测量、本机同内核三进程、epochLength=2/3s 出块/5s anti-entropy；
  margin=200 是本拓扑的数据点，不是通用最优值；
- 未测：真实多机网络分区下的补票带宽、超长宕机（>margin 仍不够）、
  `max-votes` 上调的副作用；
- 本切片**未改任何产品代码/默认值**——只产出决策依据。

## 五、边界（勿夸大）

- 单次测量、本机同内核三进程；结论只对"peer 持有全量历史票 + 本拓扑参数"
  （epochLength=2、3s 出块、5s anti-entropy）成立；
- 不测：真实多机网络分区下补票带宽、`max-votes` 上限的副作用、
  超长宕机（数千 epoch）时的行为；
- **本切片不改产品默认值**——只产出决策依据。
