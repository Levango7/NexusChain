# 方案 PLAN-053：CI 排队对照测量（roadmap #32 待复核项收口）

- **状态**：进行中（2026-10-28）
- **前置**：PLAN-024（runner 标签 26.04→24.04，归因修正：排队主因为平台侧 incident）、
  roadmap #32 的"待复核：无 incident 时段做 26.04 vs 24.04 对照测量"
- **范围**：**只读测量**——用同一 PR 的 run/job 时间戳量"run 创建 → 首个 job 启动"
  间隔，与 PLAN-024 记录的 incident 前样本对照，给出维持/回退的成本结论
- **不包含**：再切标签、改 workflow

---

## 一、问题（#32 留的待复核）

PLAN-024 把 29 处 `runs-on: ubuntu-26.04` 切到 `ubuntu-24.04`，并在文档里
如实登记：**这是低风险对冲，不宣称能缩短排队**；归因上"排队 15~60 分钟"的
主因是 GitHub Actions 平台 incident，不是标签供给。因此留下一项待复核：
**无 incident 时段的对照测量**——若 26.04 与 24.04 无差异，维持或回退成本都为零。

## 二、方法（只读，零代码改动）

用 GitHub API 对本仓最近的 run 取样（无 incident 时段），对每个 run 记录：
- `run.created_at` → 该 run 内最早 job 的 `started_at`（= 排队时长）；
- 按 `runs-on` 标签分组（ci.yml 的 job 已全是 ubuntu-24.04；
  performance-test / security-scan 等同理），并与 PLAN-024 记录的
  incident 前样本（26.04 排队 3.5 分钟、24.04 排队 4.4 分钟）对照。

**取样口径**：取最近 30 个已完成的 workflow run（覆盖 PR 与 master push），
排除官方 incident 时段（2026-10-22 15:28Z–16:41Z，PLAN-024 已记录）。

## 三、结果（2026-10-28 API 取样，60 个最近 run）

按"run created → 最早 job started"量排队时长（分钟，取整）：

| 时段（created） | 样本 | 排队 |
|---|---|---|
| 10-27 19:58 ~ 20:47 | 6 | 0 / 0 / 0 / 0 / 0 / 0 |
| 10-27 20:53 ~ 21:31 | 5 | 1 / 0 / 0 / 2 / 2 |
| 10-27 21:50 | 2 | 17（CI）/ 0（Security） |
| 10-27 22:03 ~ 22:55 | 8 | 全 0 |
| 10-27 23:37 ~ 10-28 00:09 | 9 | 全 0 |

**分布**：30 个样本中 **22 个排队 = 0 分钟**，其余 3 个 ≤2 分钟、1 个 17 分钟
（孤值，与 PLAN-024 记录的形态一致：平台侧瞬时态）。
与 PLAN-024 记录的 incident 前样本（26.04 = 3.5min、24.04 = 4.4min）对照：
**当前 24.04 的中位排队为 0 分钟**，好于当时两个标签的样本。

## 四、结论与处置

1. **roadmap #32 "待复核"项收口**：无 incident 时段下 24.04 排队中位数 0 分钟，
   无回退到 26.04 的理由（当初切标签的理由本就是"低风险对冲 + 成熟供给"，
   不为缩短排队——实测也不支持"换标签能缩短"的归因）；
2. **维持 24.04**：代价（系统库安全更新晚一档）仍由 GitHub 每周重建镜像兜底；
3. **不求一般性结论**：单仓 ~30 样本、平台侧 incident 不可排除，本结论只对
   "本仓当前时段"有效；若未来再现 15 分钟级排队，先查平台状态页再动标签。

## 五、边界（勿夸大）

- 单仓、样本量有限（几十个 run），**不是统计学结论**——只是一次对照测量；
- 平台侧 incident 无法排除未来再发生，排队时长对平台状态高度敏感；
- 本切片不改任何 workflow/标签。
