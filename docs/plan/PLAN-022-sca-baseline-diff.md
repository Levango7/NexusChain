## 一、问题：#177 带来的增量盲区

#177 把 PR / push 路径的 SCA 扫描改成「只读 NVD 缓存库」（`-Dodc.autoupdate=false`），
门禁耗时从 8.8~36.3 分钟降到 **46~66 秒**，且不再被 NVD 取数拥塞卡死（那会阻塞**所有** PR）。

**代价**：扫描用的漏洞库是**缓存库**（周级新鲜度），
所以 **PR 扫描看不到新披露的漏洞** —— 门禁判定只覆盖"缓存库里已知的那批"。

实测口径（PR #178 合并后流水线 39731888746 的报告）：

```
扫描条目 249 / 已识别 239（96%）
NVD API Last Checked = 2026-10-19T10:38:23Z   ← 缓存库时间，不是本次实时拉取
Found 52 vulnerabilities in project nexus      ← 全部低于 failBuildOnCVSS=9.0，未阻断
```

## 二、修复：基线比对

新增两件东西：

| 文件 | 作用 |
|------|------|
| `config/dependency-check-baseline.json` | **已受理基线**：当前报告里出现、且经评估可接受的漏洞（含 CVSS、命中构件、受理理由、复核日期） |
| `scripts/security/dependency-check-baseline-diff.py` | 报告 × 基线比对：**基线之外**的漏洞一律算"新增"并判红 |

接线：OWASP job 新增一步「基线比对（新增漏洞必须有人签字）」，
**只在刷新路径**（`schedule` 周 cron / `workflow_dispatch` 手动）执行 ——
此时漏洞库刚被刷新，报告里的集合与基线的差异才是"这段时间新披露了什么"。

**为什么不也在 PR 路径跑**：PR 路径用的是同一个缓存库；一旦周 cron 刷新出新的低危漏洞，
PR 路径会比对失败 ⇒ **每周一次全员被卡**。基线更新应当是**低频、有意识**的动作，
所以只在刷新路径上暴露增量，PR 路径保持"已知集合不劣化"的语义。

## 五、明确边界（勿夸大）

1. **本机制不替代升级**：它只是"让新增可见 + 逼人表态"，发现 CVE 之后**升版仍然是首选**
   （基线只记录"经评估可接受"的那些）。
2. **PR 路径仍然看不到新漏洞**（按设计，避免每周全员被卡）；发现的延迟上限 = 一次周刷新 +
   人工处理时长。
3. 基线是**人工维护**的，忘记更新会让周 cron 一直红（这正是想要的"逼人表态"，
   但也可能变成噪声 —— 需要的话可给 CI 加 `--allowlist` 窗口期豁免）。
4. 本机制**只覆盖 OWASP DC 这一条数据源**；Trivy 的结果走另一条链路
   （`scripts/security/trivy-to-issues.py` 已经在做自动分诊）。
5. 门禁阈值（`failBuildOnCVSS = 9.0`）**未改动**；是否调整属独立决策。
