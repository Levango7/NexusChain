## 一、问题（已登记，量化了根因）

**现象**：独立存储多机下，落后节点（B）追块速率 ~10–24 块/分钟 < 出块
~26 块/分钟 ⇒ 大缺口**永不收敛**（enforce 实测：B=339 vs A/C=800，差距扩大）。

**根因（代码级）**：`SyncManager.getStatus()`（`@Scheduled(30s)`）每周期：
1. **随机挑 1 个 peer** 拨 `GetStatus`；
2. 对端响应 `Status` → 本端 `onStatus`：若对端更高且 best 哈希不同 ⇒
   `server.dial(peer, GetBlocks[best, best+maxBlocksPerTransfer-1])`（默认 256）；
3. 收到 `Blocks` → `receiveBlocks`（`synchronized`）逐块校验+落库。

⇒ **一个 30s 周期最多推进一个窗口**，且窗口到达后**不续拉**——必须等下一个
30s 周期。若单窗口的实际往返/校验/落库耗时超过周期（块体 ~131KB/块、
256 块 ≈ 33MB/窗口），实际吞吐被压到远低于理论上限；再叠加随机选 peer
（可能选到同样落后的对端）与窗口被裁剪，形成"追不上"。

## 二、方案（切片 A：链式追块 + 进度守卫；切片 B：指标）

### 切片 A：有守卫的链式连续追块 —— **已交付**

1. **进度感知的续拉**：`receiveBlocks` 成功后，若
   `knownMaxPeerHeight - 本地best > 0` 且**本轮有实际推进**，立即
   （异步、非阻塞调度线程）对同一 peer 发起**下一个窗口**，不再等 30s 周期；
   在途窗口 ≤ 1（不清空队列、不并发覆盖，保持"顺序应用"）。
2. **进度守卫（防打转）**：连续 5 轮 best 未推进 ⇒ 暂停加速 60s 并限频 `WARN`
   （常规 30s 周期照跑；best 推进即恢复）。
3. **窗口自适应（保守）**：单窗口维持 `maxBlocksPerTransfer`；若实测单窗口
   往返 < 5s，可倍增（上限如 1024）——仅在配置开启时启用，默认关闭。
4. **周期性触发保留**：30s 的 `getStatus()` 不变（冷启动/掉线恢复兜底）；
   链式只做"追赶时加速"。

### 切片 A 实现落点（SyncManager，grpc-only）

- `dialStatusToRandomPeer()`：原 `getStatus()` 主体抽出（行为逐行不变），
  常规 30s 周期与加速周期共用。
- `acceleratedCatchUp()`（`@Scheduled(fixedDelay = 5_000)`）：差距 > 2×窗口
  且（无在途 或 在途超时 20s）时提前拨 GetStatus；对端响应 → `onStatus` → 请求
  下一个窗口，形成顺序窗口流水线。
- `onStatus`：发出窗口请求时记录 `catchUpWindowStop / catchUpIssuedAtMillis /
  catchUpRequestInFlight`（在途 ≤1，不并发不乱序）。
- `receiveBlocks`：批次最高高度到达/越过在途窗口上界 ⇒ 清除在途（未到
  由 20s 超时兜底）。
- 防打转：连续 5 轮（`MAX_CATCHUP_STALL`）best 未推进 ⇒ 暂停加速 60s
  （限频 WARN，常规 30s 周期照跑）；best 推进即恢复。
- `shouldAccelerateCatchUp(...)`：**纯函数**判定（单测 5 例锁定阈值/在途/超时）。

### 切片 A 实机量化（2026-10-25 晚，B 全量重置制造大缺口）

| 指标 | 切片 A 前（同日早些 enforce 实测） | 切片 A 后（本次） |
|---|---|---|
| 窗口请求节奏 | ~1 次/30s（单周期单窗口） | **73 次 / 13.2 min（~1 次/11s）** |
| B 追块速率 | ~24 块/分（不收敛，gap 扩大） | **~190 块/分**（gap 净收敛 ~164/分） |
| 示例进度 | — | 06:27:09 `1..256` → 06:40:20 `2479..2734` |
| 防打转触发 | — | `paused=0`（全程有推进，守卫未误触发） |
| invalid block | — | 38 条，全部为追赶期 A 的**推送块**（高度跳跃被拒，非窗口块） |

- **结论（如实）**：追块吞吐 ~8×（24→190 块/分），**净收敛转为正**
  （+164/分）；缺口 ~5700 的理论收敛时间从"永不收敛"降到 ~35 分钟。
  B↔A 外拨可达性是本次测量的前提（见下条边界）。
- **环境注记（重要，非本切片引入）**：B 对 A 的**外拨**若打向 A 的广告地址
  `host.docker.internal:9235`，在 WSL 内被解析到防火墙挡掉的 LAN IP ⇒ windows
  至窗口请求全部失败（仅 inbound 推送流可用，且因高度跳跃被拒）⇒ B 卡 0。
  本次测量通过把 A 的 `--p2p.address` 临时改为网关 IP 使外拨可达。
  **这是独立的环境/拓扑问题**（多机拓扑下"广告地址"与实际可达地址不一致），
  已如实登记，**不属于**本切片修复范围。

- 新增计数器/日志限频：追块轮次、窗口块数、实际落库块数、单窗口耗时、
  连续零推进次数；`GET /consensus/status` 或既有观测端点附带
  `catchUp: {gap, inFlight, lastWindowBlocks, lastWindowMillis}`（只读）。

### 明确不做（本方案）

- **多 peer 并行取块**：收益明显但需要"乱序缓冲 + 顺序应用 + 分片去重"，
  复杂度高；待切片 A/B 实测后再评估（第二切片）。
- **区块体瘦身**：单块 ~131KB（`blockSize` 字段 131454）疑似可优化，但牵涉
  序列化契约与签名，独立课题。

## 三、回归与实测口径（预登记，防事后粉饰）

- 单机可复现：可控地制造缺口（重置 B 库 + 只启动 A/C 出块 N 分钟），
  量化"缺口收敛时间"（本方案前 vs 后）；目标：**净收敛速率 > 出块速率**
  （gap 单调缩小至 < 阈值）。
- 多机回归：三节点全量重置 → 稳定后停 B 10 分钟 → 恢复 B，记录
  `gap(t)` 曲线到收敛；附 `catchUp` 指标。
- 既有回归必须全绿：`SyncManagerValidatorSetRelayTest`、F2/F1/F3 相关全量。
- **不夸大**：若实测仍不收敛，如实登记（届时评估切片 B2 并行取块）。

## 四、风险与边界

- 触碰共识同步热路径：改动集中在 `SyncManager` 的"何时再要一个窗口"，
  **不改区块校验/落库语义**（`receiveBlocks` 不重写）；在途 ≤1 保证顺序。
- 链式追块可能加剧带宽占用：窗口上限/退避/进度守卫三重约束；仅"有推进"
  才续拉。
- grpc 专属；rest 形态走 `SyncClient`（PLAN-029/032），互不影响。
