### 取证三步（都有实测）

1. **写入侧无闸门**：`JdbcFinalityStateStore.markFinalized(epoch, byte[])` 直接
   `hashStr()` 落库，不校验长度。H2 探针实测能写 3 字节（`010203`）与 0 字节行。
2. **生产路径确实能到达**：`markFinalized` 唯一生产调用点是 `FinalityGadget:891`
   （私有 `tryFinalize`）。`tryFinalize` 的 5 个调用点中 4 个已过 32 字节校验，
   但 `restoreFromStore()` 的「已终局分支」**不是**——它把键无条件写进
   `epochCheckpointWeights`（`hasValidCheckpointKey` 只挡"建索引"、**没挡"进集合"**），
   随后 `sweepFinalization("startup-restore")` 会遍历它。
3. **后果实测**：3 字节已终局行的 `gadget.isFinalized()` 返回 **false**，
   而库里仍写着该行 ⇒ **长期 DB/内存视图不一致**，且每次重启都把同一行重新载入、
   永不清除。

## 设计取舍

| 决策 | 理由 |
|---|---|
| **checkpoints 单独一张同构隔离表**（`finality_checkpoints_quarantine`） | 该表主键是 `(epoch, checkpoint_hash)`、**没有 `validator` 列**；硬塞进 votes 隔离表就得给 validator 编哨兵值，而**审计表一旦说谎就无法可靠反查**。"搬回哪张表"由**表身份**决定，不靠判别列（判别列自己也会漂） |
| **修订 `001` 而不新开 `002`** | ① `migrations/pg/` **不在**迁移棘轮门禁作用域内（已核验 `check-migration-version-ratchet.py` 只认 `<模块>/db/migration/V<n>__*.sql`，实测 115 支 / 5 个目录不含它）；② `001` **从未在任何真实环境执行过**；③ 语义上同一件事（`001` §4 的 `invalid_in_checkpoints` 早已把缺口写进脚本） |
| **`migration_id` 区分来源** | votes 用 `PLAN-069/001`、checkpoints 用 `PLAN-071/001`，回滚据此分别收窄，不会把 checkpoints 的行搬回 votes（列都对不上） |
| **§3b 同样带 EXISTS 双保险** | 宁可留脏行，也不静默丢数据 |

> **已写进 `docs/db-schema-versioning.md` 的约束**：一旦 `001` 在任一真实环境执行过，
> 后继任何变更**必须新开编号**，不得再就地修订。

## 边界（勿引用为更强结论）

1. **脏行不能由外部攻击者通过网络制造**：`submitVote` 与收敛路径都在建键前
   `hasValidCheckpointHash` fail-closed（PLAN-067 已证）。本切片的脏行只能来自
   **迁移前历史库**或**手工/脚本直接写库** ⇒ 这是**历史污染 + 视图不一致**问题，
   **不是可达攻击面**，优先级 P2；
2. **未在生产/预发库执行**：全部演练在本机 WSL2 PG 独立库；真实执行由运维按
   `docs/db-schema-versioning.md` §三.2 的升级窗口流程进行；
3. **不为 `markFinalized` 加运行时防御**：那会改变 `JdbcFinalityStateStore` 的存储层
   契约，且现有 5 处测试刻意用 3 字节哈希测「任意字节可存取」——是另一个需要单独
   决策的改动。本切片只清数据、不改行为；
4. **不做自动清洗**（§三.3 明确启动只做版本校验），脚本必须人造、人审、人执行；
5. **不处理 `finality_vote_outbox`**：需先确认其脏行是否会传播到最终性视图；
6. **同内核单机**：非物理多机，不构成分布式/集群结论；
7. 未触碰真实 L1 / 桥资金 / wallet / settlement lane，未修改他人分支/PR。
