## 二、先纠错：原提法的「高基数」前提不成立

PLAN-068 的遗留项写的是「吞吐/**基数**基准（**高基数**下 `phase × reason` 的抓取开销）」。
认领前查代码发现**这个前提是错的**：

- `FinalityRejectionCounter.Reason` = **9 项闭合枚举**；
- `Phase` = **3 项闭合枚举**；`FinalizeReason` = **1 项**；
- `FinalityRejectionMetrics` 的 map 键是 `long`（两个 `int` ordinal 打包）与枚举
  `name()`，都是 `ConcurrentHashMap` ⇒ **键集合由编译器保证有界**。

⇒ 序列数上限 = 9×3 + 1 = **28，与流量、验证人数、攻击者地址数无关**。
PLAN-066 刻意不给 counter 加 `validator` 地址标签，正是为此（其文档已记录该取舍）。

**若照原提法做，会写一个测不出问题的压测**；更糟的是，可能有人为了"减少基数"
把有用的 reason 标签合并掉。故本切片改测真正未验证的两件事。

## 三、实测（Micrometer 1.16.7 + prometheus-metrics 1.4.3，与仓库依赖一致）

### 3.1 抓取开销随序列数

| 序列数 | scrape 平均耗时 | 抓取文本 |
|---|---|---|
| 1 | 0.0469 ms | 172 字节 |
| 9 | 0.0695 ms | 764 字节 |
| 27 | **0.0749 ms** | **2096 字节** |

1→27 序列耗时只涨约 **1.6 倍**（固定开销占主导），**不是 27 倍**。
按 30s 抓取间隔，27 序列下每日约 `2 KB × 2880 ≈ 5.8 MB`。

### 3.2 并发

27 序列下（一端 200k 次 `increment`、一端连续 scrape 2000 次）：
平均 **0.0433 ms**、最差 **1.5466 ms**（JIT/GC 噪声量级，非锁竞争），
结束后序列行数 **27**（无丢失、无重复）。

### 3.3 稀疏序列语义（**纠正了我自己在预查阶段的错误假设**）

我预查时写「Micrometer 在 counter 从未 increment 时**不注册**该序列」——**实测是错的**：
`Counter.builder(...).register(registry)` 一旦执行，即使 count 为 0，抓取文本里就有那一行：

```
nexus_finality_vote_rejected_total{phase="admission",reason="checkpoint_hash_invalid"} 0.0
```

但**生产用的是 `computeIfAbsent` 懒注册**（只在首次拒绝时 `register`），所以生产上
「从未发生过的 reason」**确实不会**出现。这个差异必须写清，否则后人会把
「序列没出现」误判成「指标坏了」，进而错误地改成预注册全量。

### 3.4 稀疏序列不破坏告警

- `increase(<不存在的序列>[10m])` 返回**空向量**（不是 0）⇒ `> 0` 恒为空 ⇒ **不误报**；
- 首次拒绝后序列**立刻**出现且值为 1 ⇒ 下一次规则评估即可触发 ⇒ **无延迟窗口**。

## 四、门禁 `FinalityRejectionScrapeBudgetTest`（4 例）

| 用例 | 钉住什么 |
|---|---|
| `fullVocabularyStaysWithinScrapeBudget` | 票级序列条数 = 9×3、检查点级 = 1；**每个序列的标签键必须严格等于 `{reason, phase}` / `{reason}`**；文本体积 < 28×200 字节 |
| `unReachedReasonsAreAbsentBecauseRegistrationIsLazy` | 一次拒绝都没有时 0 条；只触发一种时恰好 1 条；未触发的 reason 不得出现 |
| `missingSeriesDoesNotBreakAlertSemantics` | 首次拒绝后立刻可见且值为 1（无延迟窗口） |
| `cardinalityBudgetMatchesClosedVocabulary` | 预算常量与枚举组合数一致；PLAN-070 文档必须写明上限 |

全部断言**结构性事实**，**不断言绝对耗时**——绝对耗时会因机器/负载 flaky。

## 五、反向对照（2 组，并抓到门禁自己的一个真实缺陷）

| B | 改预注册全量（构造时注册 27 条） | 稀疏序列两例红（预期 0 条，实际 **27** 条） |

```

```

还原后 `--rerun-tasks` 重跑 4/4 绿。

### 抓到的缺陷（值得记，因为它是"红了哪一条"的直接实例）

最初的预算断言只数「序列行数」：

```java
text.lines().filter(line -> line.startsWith(name + "{")).count()
```

给 counter 加 `validator` 标签后，每个 `(reason, phase)` **仍然只有一行** ⇒
条数仍是 7、体积只涨几十字节 ⇒ **预算断言完全不红**。当时那次"红"其实是另一条
用例（标签字面量拼接不一致）意外变红的，属**"红得不精确"**。

修法：解析并断言**标签键集合**。修正后变异 A 的报错才明确指向
`实际 [phase, reason, validator]`。

⇒ 教训：反向对照不能只看"有没有红"，必须看**红的是不是那条该红的断言**。

## 七、边界（勿引用为更强结论）

1. **不是压力测试/容量规划**：只测单进程抓取端在"序列数上限"下的开销量级，
   **不测** Prometheus 服务端的存储/索引/查询成本——那需要真实 Prometheus +
   真实数据量，属监控平台侧；
2. **同内核单机**：数据来自一台 Windows 机器上的 JVM，**不是物理多机**，
   也不代表生产硬件（CI runner / 云主机）的绝对数值；
3. **未起真实 Prometheus/Alertmanager**：稀疏序列的告警语义由 PromQL 语义与
   Micrometer 行为**推导 + 单测**确认，未在真实规则评估循环里观测；
4. **不改生产注册方式**：懒注册是刻意设计（避免无界序列），本切片只把它钉住；
5. **绝对耗时只作文档记录**：门禁不断言耗时，避免机器差异造成 flaky；
6. 未触碰真实 L1 / 桥资金 / wallet / settlement lane，未修改他人分支/PR。
