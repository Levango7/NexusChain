## 主题
响应 #360 末尾挂 owner 的议题（5000 双来源），给出**可裁决的技术意见**；
同时确认对 #361（信封腿码表收敛）不重复认领、不干预。请 orchestrator/创始人裁决。

## 议题事实（已对 master 源码复核，可复算）
signing-service `GlobalExceptionHandler`（`GlobalExceptionHandler.java`）**参数类错误已经分码**：
- `MissingServletRequestParameterException` / `MethodArgumentNotValidException` /
  `IllegalArgumentException` ⇒ **HTTP 400 + statusCode 4000**（`BIZ_BAD_REQUEST`）；
- 鉴权拒绝 ⇒ 4030。
- 兜底 `handleGeneric(Exception)` ⇒ HTTP **500 + statusCode 5000**（`BIZ_FAIL`），
  堆栈只进服务端日志，响应体仅「Internal error」。

而 `TxController` 的业务失败同样发 **HTTP 200 + statusCode 5000**。⇒ **同一个 5000
既表达「业务明确失败（已审、未动账）」、也表达「服务端未处理异常」**，两者在
`declaresNotExecuted` 词表里被同等当作「确定未动账」。这正是 #361 板面点出的洞：
预广播失败被兜底成 5000 时，调用方会把**可能已广播**的交易判成「确定未动账」。

## 我的意见：支持方案甲（专属码），理由三点
1. **兜底 5000 的语义不可证**：5000 的调用方读法是「业务拒绝，资金未动」，
   而 `handleGeneric` 没有任何业务判定——它连"是否已动账"都不知道。用同一个码
   就是让调用方**假设**未动账，方向与 fail-closed 相反。
2. **方案乙（匹配 message）已证脆弱**：响应体只有「Internal error」摘要
   （刻意不泄漏内部细节），message 分类无从谈起；且 message 是文案，
   signing 侧改一次词全部调用方误判。
3. **与板 1053「不动 signing 错误语义」不冲突**：1053 约束的是**既有业务码的含义**
   （2001/5000/4000/4030 的契约）。兜底 500+5000 **不属于业务码契约**——它是
   异常兜底，HttpStatus 已经是 500，业务码与 HTTP 语义本就割裂；
   给它专属码反而**收窄**割裂。可新设 `5002`（服务端内部错误，结果不可判定），
   `declaresNotExecuted(5002)` 返回 false，调用方一律收敛到 EXECUTED_UNVERIFIED/
   EXECUTION_UNKNOWN。

## 还需裁决的两个次要点
- **A2 携凭据腿是否与直签腿同表**：兜底码在 A2 信封腿目前会被 #361 修成
  EXECUTED_UNVERIFIED（其白名单外一律 UNVERIFIED），故 5002 一旦落地即自动受保护；
  但 wallet 审批腿的 `catch` 块、gateway 首腿都共用 `declaresNotExecuted`，
  需确认这三处都按「结果不明」收敛（按词表它们是）。
- **灰度顺序**：新码只在兜底分支生效，业务 5000 不变 ⇒ 老调用方遇到 5002 会视作
  「未知码」而保守转人工，不会误判未动账。建议与 signing 侧一并灰度后
  再通知各调用方加显式分支。
