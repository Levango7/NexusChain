## 一、取证（H2 + 真实 store / gadget / outbox）

用一条**签名完全有效、仅哈希长度非法（3 字节）**的票 —— 这样才能证明是「长度闸」
在起作用，而不是「签名坏了」这种无关原因。临时探针跑完已删除，结论固化进门禁。

| 问题 | 实测 |
|---|---|
| 脏票能进 outbox 吗？ | **能**。`enqueue()` 只挡 `vote == null`，不校验长度 ⇒ `pendingCount=1`、表 1 行 |
| 重放会怎样？ | **正常拒绝并移除**。`flush() → tryFlush() → submitVote()`，`submitVote` 先走 `validateVoteBinding`（含 PLAN-067 的 32 字节校验）返回 `finalized=false`（**不抛异常**），而 `tryFlush` **只在 catch 到异常时**才留着重试 |
| 会变毒丸吗？ | **不会**。连续 3 轮 `flush()` 后内存队列与 outbox 表都归零 |
| 会污染最终性视图吗？ | **不会**。`finality_votes` / `finality_checkpoints` 均 0 行、`isFinalized()` false、内存 voter 集合空 |

## 二、三张表的行为对比（本切片核心结论）

| 表 | 写入侧校验 | 脏行是否沉淀 | 需要清理 |
|---|---|---|---|
| `finality_votes` | 无 | **是**（每 5s 被收敛路径重扫） | ✅ PLAN-069 已隔离 |
| `finality_checkpoints` | 无 | **是**（经 restore 已终局分支进 weights，DB/内存视图不一致） | ✅ PLAN-071 已隔离 |
| `finality_vote_outbox` | 无 | **否**（重放时被 `submitVote` 正常拒绝并移除） | ❌ **不需要** |

⇒ 这解释了为什么 PLAN-069/071 只处理那两张表：**outbox 是「写库意图」的暂存，
它的出口 `submitVote` 本身就是 fail-closed 的**。脏票在这里只是「一次失败的尝试」，
不是「沉淀的事实」。

## 六、一个必须登记的隐含依赖

本结论前提是「`submitVote` 对非法哈希**正常拒绝**而非抛异常」。若将来改成抛异常，
脏票会变成**毒丸**（每 5 秒重试一条永远失败的票、永远留在 outbox）——门禁会红，
但修复需要新代码（例如按 `attempts` 上限丢弃并计数）。
