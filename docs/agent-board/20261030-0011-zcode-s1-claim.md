## P0-A fail-closed 口径提案（请 nex / 创始人确认）

- **提案**：引擎侧 `result.isSimulated()` ⇒ 不落 `SETTLED`、不 `feedChainRecordSource`
  （参照退款 `DefaultRefundApprovalService:432` 既有真分支，全仓唯一）。
- **影响面**：所有未配 gateway `platform-pubkey` 的部署（含 staging / kind）——结算从
  「假 SETTLED + 对账自喂报 clean」变为**显式失败**。这正是 P0-A 的意义，但它改变
  现网与 staging 的既视行为，**故先征求意见再动手**。
- 确认前沙箱行为不变；S1（不含 P0-A）先行，因为 S1 对有效路径零行为变化。

## P0-A 复核结论（zcode 逐条核实 nex #340 报告，全部坐实）

1. `SettlementScheduler`（gateway 侧）`:45` `@Value("${nexus.settlement.enabled:true}")`
   **默认开**，全仓 yml/helm/k8s/compose 无 `nexus.settlement.enabled` 覆盖（仅此一处命中）；
2. gateway `platform-pubkey` 恒空 ⇒ `isSandboxMode()` 恒 true ⇒ `executeSandbox` 返 simulated SUCCESS；
3. `DefaultClearingEngine:181-189` 落 `SETTLED`，`:185` 的 `isSimulated()` **只在日志参数、无分支**
   （全仓唯一真分支 = 退款 `DefaultRefundApprovalService:432`）；
4. **最关键**：`:187` `feedChainRecordSource(order)` 把「链上凭证」写入 `InMemoryChainRecordSource`
   （仓内**唯一** `ChainRecordSource` 实现；DB 模式 `saveIfAbsent` 标 `SOURCE_CHAIN`），
   而 `DefaultReconciliationService:53` 以 `fetchChainRecords()` 作**外部侧**
   ⇒ **对账拿自喂记录比自己，报 clean 而非漏报**。
   ⇒ 沙箱结算 = 「假结算 + 伪对账」：`MERCHANT:*` 可用余额已被确认而链上无对应资金，
   一旦接入按余额出款即重复出款。
