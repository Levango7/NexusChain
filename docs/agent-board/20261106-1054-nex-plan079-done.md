## 结论先行

真实 PostgreSQL 复核了 PLAN-072 的「outbox 脏行不传播」结论（正确小写 origin 的
脏行处理一次即被拒并移除），并修复了一个由此暴露的隐藏鲁棒性缺口：
**legacy/手工 `origin` 大小写不一致时，`removePendingVote`/`markPendingVoteFailure`
静默 0 行**，导致该行每 ~5s 重放（人工毒丸形态）。

## 一、真实 PG 取证（同内核单机）

| 场景 | 结果 |
|---|---|
| 正确小写 `origin='local'` 的 3 字节哈希脏行 | 启动恢复**只处理一次**（日志 3 行，无重复）、`submitVote` 长度闸拒绝、行被移除；`outbox=0 / dirty=0 / vote_rows=0 / dirty_votes=0` |
| 错误大写 `origin='LOCAL'`（修复前） | 行删不掉、每 ~5s 重试（**人工毒丸**：本切片要消除的形态） |
| 修复后的同一大写行 | 处理一次即被移除；`outbox=0 / votes=0`，无重复重试 |

⇒ PLAN-072 结论对**应用自己写入的行**不变；缺口只在 legacy/手工数据触发。

## 二、修复与门禁

- `JdbcFinalityStateStore.removePendingVote` / `markPendingVoteFailure`：
  origin 匹配改 `LOWER(origin)=LOWER(?)`，0 行时 `log.warn`（epoch/validator/origin）；
- `JdbcFinalityStateStoreTest` +2 例：legacy 大写行「可删除」「可计 attempts」；
- 反向对照 A：删除查询改回精确等值 ⇒ 第一例精确红（`expected <0> but was <1>`）；
- 反向对照 B：失败更新改回精确等值 ⇒ 第二例精确红（`expected <1> but was <0>`）；
- 还原后 11/11 绿。

## 四、边界（勿夸大）

1. **同内核单机**（WSL2 PG 16.15 + 单进程 core），非物理多机；
2. 触发源是 legacy/手工行；不能据此称「现有 outbox 会毒丸」；
3. `LOWER(origin)` 不再命中原 PK 索引；outbox 常态极小（应用队列每 origin ≤256，
   库行短暂滞留），可接受；行量增长需再评估；
4. 不改重试策略 / attempts 上限 / 自动清理（PLAN-072/073 登记不变）；
5. 未触碰 L1 / 桥资金 / wallet / settlement 契约。
