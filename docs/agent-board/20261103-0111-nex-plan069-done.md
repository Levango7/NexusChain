### 设计要点

| 决策 | 理由 |
|---|---|
| **隔离而非删除** | 直接 `DELETE` 不可回滚。搬运到 `finality_votes_quarantine`（含 `reason`/`quarantined_at`/`quarantined_by`/`migration_id` 四列审计）后生产逻辑等效看不到脏行，但数据可查、可导出、可**原样搬回** |
| **口径与生产逐字一致** | `length(checkpoint_hash) = 64 AND checkpoint_hash ~ '^[0-9a-fA-F]{64}$'`，对应 `hasValidCheckpointHash()`（32 字节）+ `hashStr()`（`HexFormat` ⇒ 64 位小写 hex，读回 `hexToBytes` 非 hex 解成 null）。口径不一致是**双向**破坏：更宽漏删、更严则把合法票搬走 |
| **§3 带 EXISTS 双保险** | 若 §2 因故少搬一行，§3 就不删它——**宁可留脏行，也不静默丢数据** |
| **回滚是真回滚** | 按 `migration_id` 把行原样搬回，且**不删除隔离表**（审计痕迹必须留）。搬回安全：这些行仍被生产侧判为脏行 |
| **版本号保持 1** | DDL 只有 `CREATE TABLE IF NOT EXISTS`（additive-only），数据搬运不改表结构；按 §三.2 仍必须是脚本 + 人工执行（属数据重写），但版本号表达的是**结构契约**、不是「跑过数据脚本」——与 PLAN-018 同一口径。已在 `docs/db-schema-versioning.md` 新增 §三.4 台账写明该判定 |

脚本结构：§0 幂等建表 → §1 审计（只读）→ §2 搬运（`ON CONFLICT DO NOTHING`）
→ §3 移除（三列主键 `EXISTS`）→ §4 自检（`remaining_invalid` 必须为 0）。

### 反向对照抓到三个真实缺陷（所以实现被改过，如实记录）

1. **口径断言被别处文本蒙混过关**：最初写在对**整份 SQL** 的 `contains()` 上，
   §1 审计段 / §2 搬运段 / §4 自检段都有同样文本 ⇒ 只改坏 §3 DELETE 时断言仍为真、
   门禁形同虚设。改为 `statement(...)` 截取单条语句后逐语句断言。
2. **DELETE 的 `EXISTS` 检查同样是整份 SQL 级**：`substring(deleteAt).contains(...)`
   仍能在前文命中。改为截到分号，并额外要求**三列主键都参与匹配**
   （只按部分列会误删同 epoch 其他验证人的行）。
3. **迁移脚本不在 Gradle test 任务输入里**：改坏 SQL 后跑测试，Gradle 判
   `UP-TO-DATE` 直接跳过，输出 `BUILD SUCCESSFUL in 3s`——本地「绿」而门禁**从未执行**。
   按 `build.gradle` 里 PLAN-062 的先例补
   `inputs.dir("${rootDir}/migrations/pg")`，实测改 SQL 后不再跳过（红）、还原后绿。

## 边界（勿引用为更强结论）

1. **未在生产/预发库执行**：所有演练都在本机 WSL2 PostgreSQL 16.15 的独立库上；
   真实执行由运维按 `docs/db-schema-versioning.md` §三.2 的升级窗口流程进行，
   本切片只交付脚本 + 回滚脚本 + 门禁 + runbook；
2. **不做自动清洗**：§三.3 明确「应用启动只做版本校验，不做自动升级」，
   本切片不破坏这条。脚本必须**人造、人审、人执行**；
3. **同内核单机**：WSL2 里的 PG 与 Windows 侧的 Java 同属一台物理机，
   **不是物理多机**，不构成分布式/集群结论；
4. **不处理 `finality_checkpoints`**：脚本 §4 只**报告**其脏行数
   （`invalid_in_checkpoints`），不搬运。该表脏行的来源与语义需另行确认，属后续切片；
5. **不做通用 retention**：只处理「格式非法」的行，不处理「合法但过旧」的行；
6. **回滚不抹审计**：隔离表在回滚后仍保留，这是有意的；要彻底清空审计痕迹是
   另一个需要显式决策的动作；
7. 未触碰真实 L1 / 桥资金 / wallet / settlement lane，未修改他人分支/PR。
