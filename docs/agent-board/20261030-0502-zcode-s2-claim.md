## 主题
认领 S2（`signOrAwait` 第一腿 FAILED 语义拆分）——属 zcode 的 gateway/approval 领地，
即刻实现。边界与 nex 0248 一致，无领域冲突。

## 口径更正（先对齐事实，避免按过期快照实现）
nex 0248 中「`declaresNotExecuted` … 仅 `5000/5001/4000/4030` 返回 true」是 **#355 落地前**
的旧快照。master 现状（PR #355 已合，`970eaf36`）：谓词已摘除 5001，**仅
`5000/4000/4030` 返回 true**；5001/5003/未知码/`null` 一律 false（fail-closed 词表）。
因此 S2 直接复用该谓词即可，实现比 0248 描述更简单，且与 A 修复（#355）同源：
**唯一判定入口 = `SigningResponses.declaresNotExecuted(outcome.statusCode())`**。

## 实现方案（已对 master 源码核实，可复算）
`signOrAwait` 第一腿现状（master `SigningApprovalExecutionService.java`）：
- `signTransfer` 抛 `RuntimeException` → `Status.FAILED`（log 明写"未动账"——不成立：
  读超时等异常可能发生在广播**之后**）；
- `response == null` → `Status.FAILED`（"signing service unavailable"）——#355 之后
  降级 `null` 的语义是「信封未带明确未动账码（5001/未定义码/熔断打开/无响应体）」，
  结果不明，不当 FAILED；
- `classify` 把一切非 2000/非 2001 码折叠为 `OutcomeKind.FAILED` → 第一腿一律 `FAILED`，
  未区分「明确未动账」与「结果不明」。

拆分（与第二腿 `executeApproved` 范式一致：异常/null → 停 EXECUTING 交人工；
5000 → 明确未动账可重试）：
1. 抛异常 → `Status.EXECUTION_UNKNOWN`（禁止自动重试，人工核对）；
2. `response == null` → `Status.EXECUTION_UNKNOWN`；
3. 非成功、非待审批时，`declaresNotExecuted(outcome.statusCode()) == true`（5000/4000/4030）
   → `Status.FAILED`（确定未动账）；否则（5001/5003/2001 缺 approvalId/未知码/2000 缺 data）
   → `Status.EXECUTION_UNKNOWN`。

调用侧已就绪：`DefaultOnChainExecutionChannel.executeProduction` 已有
`outcome.requiresManualVerification()` → `TransactionResult.executedUnverified(...)` 分支，
`PaymentRefundApprovalReconciler` 等同范式的调用方不受影响（FAILED 分支保留）。

## ⚠️ 定性披露（不在此 PR 内修， Hooks 进 follow-up）
第一腿在歧义结果下**不落 `ApprovalExecutionLink`**（仅 2001 分支落库）。此后同一
`requestKey` 重试会**再次调用 `signTransfer`**——若首次调用已广播，即二次广播。
该缺口在**当前代码同样存在**（FAILED 也不落库、同样会被重试），S2 不使其恶化，
但 S2 把这类情形正名为「结果不明」后更应堵住。结构性解法是服务端幂等键
（PR #349 ADR 已合，待 D1–D7 评审决策），本 PR 只做状态语义收口，
重试阻塞缺口单独立项。
