NexusChain 现状审计：微服务化后三项功能评估

审计日期 2026-08-07 ｜ 基线版本 v1.6.0（Phase 4 微服务化完成） ｜ 范围：MPC 多方签名 / L2 Rollup / PoS 出块（DefaultPosConsensus.propose）

核心结论（先读这里）

三项功能都还需要做，但性质完全不同：

  • MPC GG18/GG20 — 编排层（DKG 轮次、签名会话、消息路由、传输、WAL、加密存储）全部就绪，核心密码学全是 TODO（Paillier / Feldman VSS / MtA / ZK 证明 / 份额合并）。壳已备好，芯是空的。这是工程量最大的一项。
  • DefaultPosConsensus.propose — 纯占位实现（抛 UnsupportedOperationException）；@Primary 的 PosConsensusEngine.propose() 返回 null、validate() 恒 true。周边设施（质押/验证人/奖励/罚没）已真实，只差出块主链路；且 @Primary 空实现是"静默地雷"。
  • L2 Rollup — Optimistic 协议逻辑真实度 80%（MPT 状态根、单步二分欺诈证明、挑战窗口、bond、first-valid-wins、EIP-4844 blob、gas 估算），但零测试、L1 集成是内存模拟；ZK 是纯骨架（ZkProofSystem 抽象 + 电路壳）。

建议执行顺序：第一批（快赢排雷）：L2 Optimistic 测试补全 + PoS 出块接线；第二批（核心工程）：MPC 密码学引擎；第三批（按需）：L2 L1 真实化 + ZK 证明系统。详见第五节。

三、需求分析

3.1 MPC 多方签名

目标

让 signing-service 的 MPC 从"编排壳"变成可用的门限 ECDSA：t-of-n 参与者分布式生成密钥、分布式签名、产出可在链上验证的标准 ECDSA 签名，私钥份额永不离开参与者节点。

验收标准
  • 2-of-3 与 3-of-5 场景 DKG + 签名端到端跑通，签名可被标准 ECDSA 验证器（BouncyCastle/链节点）验证
  • 少于 t 个参与者无法完成签名（quorum 强制）
  • 份额泄露 < t 份不泄露私钥（协议级安全属性，通过协议向量测试保证）
  • 与参考实现互签互通（协议兼容性向量测试）
  • nonce 复用防护生效（GG18 已知攻击面，NonceTracker 已验证）
  • ColdWalletMultiSigService 全流程（initMultiSigTransfer → participantSign → aggregateAndBroadcast）接入真实引擎

3.2 PoS 出块主链路

目标

PosConsensusEngine.propose 从返回 null 变为真实出块：选取提案者 → 从交易池打包 → 构造区块 → 提案者签名 → P2P 广播；validate 从恒 true 变为完整校验链。DPoS 保留为默认共识，PoS 通过配置切换（渐进替换，避免一次性切换风险）。

验收标准
  • propose() 产出签名区块：含交易池打包交易、提案者签名、合法时间窗口
  • validate() 校验：区块签名 → 提案者 ∈ 活跃验证人集合 → 质押满足门槛 → 时间窗口 → slash 条件
  • 双节点集成测试：PoS 模式下可连续出块并被对端验证
  • ConsensusConfig 支持 dpos|pos 切换，切换不破坏现有链
  • 移除或禁用 @Primary 空实现（未完成前防止误注入）

3.3 L2 Rollup

目标

分两层：Optimistic 先把已写好的协议逻辑用测试固化（当前零测试是最大风险），再决定是否做真实 L1 合约集成；ZK 接入真实证明系统（骨架 → 可用）。

验收标准（Optimistic 优先）
  • FraudProofVerifier：Merkle 证明、二分定位、挑战窗口、bond 罚没、first-valid-wins 全覆盖单测（含恶意提交者场景）
  • StateRootManager / RollupSequencer / Eip4844BlobCarrier 单测
  • 端到端：submit → challenge → rollback → finalize 全流程测试（含挑战失败罚没 bond）
  • ZK：ZkProofSystem 接入真实实现（halo2 或 Plonk 系），prove/verify 端到端跑通，电路为 Rollup 状态转换

四、技术方案与关键决策

4.1 MPC：集成成熟库，不重造密码学轮子

GG18/GG20 的核心（Paillier 同态、Feldman VSS、MtA、ZK 证明）是安全审计密集型工作，自研风险极高。Java 生态无成熟 GG18/GG20 实现，成熟代码集中在 Rust（multi-party-ecdsa / tss-lib）与 C（Zenroom）。

方案路线优点缺点建议
A（推荐）密码学引擎独立进程（Rust multi-party-ecdsa / tss-lib），signing-service 通过本地 gRPC/HTTP 调用，现有编排层（RoundBarrier/状态机/传输）继续复用协议实现成熟、审计充分；与现有微服务架构一致；编排层零重写需引入 Rust 构建/部署链路首选
BZenroom 绑定（C 库 JNI）单进程、无额外服务绑定维护成本；Zenroom 门限签名 API 覆盖需验证备选
C纯 Java 自研（BouncyCastle + 自实现 Paillier/ZKP）无外部依赖数月工程量 + 安全审计成本，风险高不推荐

关键点：现有 mpc 包已经定义了干净的边界（传输/会话/聚合），密码学引擎作为 SPI（MpcCryptoEngine）替换即可，DKG 轮次、签名轮次、quorum 逻辑可全部保留。

4.2 PoS：复用 DPoS 出块骨架，共识可切换

  • 区块构造/打包/广播复用现有 PackageMiner / Miner / MineThread 骨架，仅替换"提案者选取"与"区块头签名"为 PoS 语义（PosProposer 已就绪）
  • validate 实现完整校验链，SlashingService 已就绪可直接挂钩
  • ConsensusConfig 增加 consensus.mode=dpos|pos 路由；PoS 未达生产标准前保留 DPoS 默认，同时把 PosConsensusEngine 的 @Primary 去掉（或改为按配置启用），消除静默 null 地雷

4.3 L2：先测试固化，再真实化

  • Optimistic：先补单测+端到端（2-3 天工作量，资产已 80%）；L1 合约客户端实现放第二阶段（现有 L1ContractClient 接口 + DefaultL2BridgeContract 内存实现，可先做契约测试锁定行为）
  • ZK：ZkProofSystem 抽象已定义好（setup/prove/verify），选型 halo2（zkSync 同源）或 Plonk 系；与 MPC 相同的"引擎进程"模式接入（Java 无成熟 ZK 库）
