# ADR-034: 高可用演进路线——从单副本到异地多活

- **状态**：Accepted（方向）/ 设计稿（各步细节随实施迭代）
- **日期**：2026-10-03
- **决策人**：项目所有者（原话定夺：「将来正式部署上线要能够解决异地灾备、异地多活、
  低延迟这些问题，现在基础条件不具备就先做能做的」）
- **配套**：数据层前置见 [ADR-033](ADR-033-database-evolution-oceanbase.md)

---

## 1. 目标态（北极星）

正式上线时满足：**异地灾备 + 异地多活 + 低延迟**，具体口径：

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| RPO | 0（数据零丢失） | 依赖 OceanBase Paxos 多副本（ADR-033）或等价同步复制 |
| RTO | < 30s（接入层切换）；< 8s（数据层自动选主） | 接入层 DNS/网关切换 + 数据层自动容灾 |
| 多活 | ≥2 地域同时服务交易流量 | 单元化路由（按商户分片），单地域故障无感切换 |
| 延迟 | 用户就近接入 | 多活的自然副产品 |

**明确放弃**：7×24 人工运维/on-call（用户 2026-10-03 决策「运维 SRE 给人家吧」）——
本路线的一切设计必须**自动收敛**，不依赖人盯。

## 2. 现状基线（2026-10-03 实测取证）

当前是**单集群、单副本、单地域**形态：

- 12 服务模块 Docker/K8s 单命名空间部署，staging+prod 各一套；
- **数据层 SPOF**：单实例 MySQL（业务库）——这是多副本路线要解决的核心；
- 已就位的多副本友好项（grep/代码取证）：
  - 幂等存储走 **Redis**（`OrchestrationIdempotencyStore` → `RedisIdempotencyStore`）——
    无状态化最关键的一项已经是共享存储；
  - 路由规则：内存态 + DB write-through 恢复（`RoutingEngine` 重启即重建）；
  - Connector 注册表：`ConnectorConfig` DB 持久化恢复；
  - 业务指标：`MetricsCollector` 进程内——指标聚合场景天然允许按实例独立再汇总；
- 多副本阻塞项（实施时逐个解决）：
  - signing-service P2P 传输：每实例独占本地端口（`mpc.transport.local-port`，
    注释已声明「每个实例需不同端口」）——多副本需 headless service + 按
    partyIndex 固定路由，或改用消息中间件；
  - mpc-engine keyshare：按节点身份持有（**设计如此**，份额隔离是安全属性非缺陷；
    多活时每个 party 的副本组独立扩，不能混）；
  - 链 core（LevelDB）：共识节点本身是多副本语义（BFT），但其 LevelDB 存储
    未做卷级冗余——依赖 K8s 存储类的多副本/快照策略兜底；
  - 定时任务：`@Scheduled` 采样/清理类任务（健康采样、审计清理）多副本会重复执行——
    已有 ShedLock 基础设施（`@EnableSchedulerLock`），逐步给新定时任务补
    `@SchedulerLock` 即可。

## 3. 演进路线（三步，每步独立可验证）

| 步 | 内容 | 验收 | 前置 |
| --- | --- | --- | --- |
| **第 1 步：单集群内多副本**（本 ADR 落地期） | 每服务 ≥2 副本跑起来，暴露真正的共享态问题；新定时任务一律 `@SchedulerLock`；P2P 传输改 headless+固定路由或改 MQ | 滚动重启任一 gateway/signing 副本，支付链路无失败（可用 L3 容量画像压测时滚动验证） | 无——纯代码/配置层 |
| **第 2 步：多可用区** | 双 AZ 部署 + 数据层多副本（OceanBase 3 副本跨 AZ，ADR-033 实施） | 拔掉单 AZ 全部 Pod，RTO<30s 自动恢复 | ADR-033 前置清单核销 |
| **第 3 步：异地多活** | 双地域 + 单元化路由（按商户分片到单元，每单元闭环交易链路）+ 全局路由层 | 单地域整体断网，另一地域无感承接（延迟抖动 <1s 级） | 第 2 步稳定运行 + 真实资金/正式上线的业务决策 |

## 4. 现阶段（基础条件不具备时）做什么

用户口径「先做能做的」——**本 ADR 的第 1 步 + 文档就是现阶段产出**：

1. 多副本阻塞项的代码层改造（P2P 路由、SchedulerLock 覆盖）——随日常开发逐步落；
2. 本文档把目标态钉死，避免后续实现与「异地多活」目标冲突的架构债
   （例如任何新增「进程内独占状态」都需先过本 ADR §2 的审视）；
3. 压测阶梯（perf/k6/README §2.1）提供每步的容量基线对比能力。

## 5. 明确不做

- 不做「为多活而多活」的提前基建（没有真实资金/上线决策前不进入第 2/3 步）；
- 不自研单元化路由中间件（第 3 步时评估开源方案 vs 自研，另立 ADR）；
- 不承担 7×24 运维（自动化收敛为设计约束，见 §1）。
