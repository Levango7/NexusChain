# ADR-038：支付执行与支付子状态承诺 V3（A2 内核）

- **状态**：Accepted，A2a 实施中
- **日期**：2026-11-25
- **Owner**：ZCode
- **范围**：支付执行结果、支付子状态编码与组合状态根，以及 `BATCH_TRANSFER` 的原子执行样例；不包含支付类型门禁放行或服务端 SDK 启用

## 1. 问题

A1 的 V2 账户根解决了余额/nonce 未承诺与顺序不确定，但支付扩展还会产生通道、仓位、桥和其他支付状态。若这些状态参与验块却只在链下数据库出现，节点仍可能对同一支付状态得到不同结论而根不变。

现有支付处理器还存在异常吞掉、部分类型只记日志、重放只跳过不拒绝等问题，不能直接接入共识执行。

## 2. 决策

1. 所有支付执行返回显式 `PaymentExecutionResult`：账户变化、支付子状态变化和实际执行手续费。失败必须抛出异常并拒绝整个结果，禁止部分写入后继续。
2. 账户与支付子状态分开编码，再以 V3 域分隔组合：
   `V3_ROOT = SHA3-256([0x03] || accountV2Root || paymentRoot)`。
3. `paymentExtensionActivationHeight` 与 A1 的 `stateCommitmentV2ActivationHeight` 独立。默认 `Long.MAX_VALUE`，合入不激活。
4. 高度前保持既有 V2/legacy 根；支付激活高度后才使用 V3。A3 门禁与该高度同步，禁止出现“支付已放行但根仍是 V2”的配置。
5. 链下 `PaymentStateStore` 只能作为索引/缓存，共识判定和状态根必须来自同一份确定性执行结果。

## 3. 支付子状态条目

每条 `PaymentStateEntry` 包含 `kind`、UTF-8 `id` 与二进制 `payload`：

| 字段 | 字节数 | 编码 |
|---|---:|---|
| 版本 `0x03` | 1 | 固定 |
| kind | 1 | BATCH=1、CHANNEL=2、POSITION=3、BRIDGE=4、IDENTITY=5、SUBSCRIPTION=6、REPLAY_KEY=7 |
| id 长度 | 2 | 无符号大端 |
| id | 可变 | UTF-8 |
| payload 长度 | 4 | 无符号大端 |
| payload | 可变 | 类型专属规范编码 |

条目按 kind 数值、再按 id 的无符号字节字典序排序；同一 `(kind,id)` 重复直接拒绝。空支付列表根为 `SHA3-256([0x03])`。非法长度、空 id、空 payload 引用或重复条目 fail closed。

## 4. BATCH_TRANSFER 原子执行

1. payload 必须是合法批量项，项数与总额受既有上限约束，总额使用 `Math.addExact`。
2. `tx.amount` 必须等于项总额；发送方余额必须覆盖 `总额 + getFeeExact()`，所有计算使用精确加减乘。
3. 发送方只扣一次总额与手续费，nonce 设为交易 nonce 且必须大于旧值并不超过 `MAX_TX_NONCE`。
4. 收款方逐项精确入账，重复地址合并；自收款仅承担手续费且结果只有一个发送方账户。
5. 任一地址、金额、余额、nonce、溢出或解析失败都使整个执行失败，输入账户不被修改。
6. 支付条目 id 为交易 hash，payload 为规范批量项编码，确保同一执行可重放得到同一 V3 根。

其他 0x10–0x1a 类型必须分别建立状态机、payload、余额守恒与重放测试，不能因 BATCH 通过就宣称全部完成。

## 5. A2a 验收

- 发送方扣款/扣费一次、nonce 正确、收款精确、实际执行手续费准确。
- 自收款与重复收款人、余额不足、金额不一致、debit/credit 溢出、nonce 边界均为确定行为。
- 输入对象在失败时不被修改。
- V2/V3 激活边界独立；账户与支付条目任意乱序仍得到相同组合根。
- 支付条目变化改变组合根；编码向量、空根与重复条目均有测试。
