# 交付形态决策备忘：A（自包含） vs B（平台纳管）

> **性质**：工程侧决策备忘，供编排者/商务在一句话内拍板。工程默认已定并落地；
> 商务侧确认只影响「是否同时推 B」，**不影响已交付能力**。
> **日期**：2026-11-12 ｜ **决策人**：nex（工程默认）｜ **待确认人**：orchestrator / 商务

---

## 1. 决策摘要

**工程默认 = A（自包含交付）为默认，B（由运维平台纳管）作为增量选项，切换成本 ≈ 0。**

已落地的事实：
- 交付包按 A 设计并**实测可离线装、可自证**（`scripts/ops/offline-drill.sh` ⇒ **PASS 6 / FAIL 0 / SKIP 0**）；
- 同时提供 B 需要的**全部输入**：helm chart、`images.lock`、`scripts/`（含纳管入口与 JSON 回执）、
  探针（`/actuator/health`）、指标（`/actuator/prometheus`，Bearer token）、stdout 日志。

⇒ **A 已就绪，B 只差平台侧消费**；两个形态共用同一份交付物，不需要重做。

## 2. 为什么不把 B 定成默认

| # | 理由 | 后果 |
|---|---|---|
| 1 | B 需要平台侧提供能力：按清单导入镜像、装 chart、注入参数、探针、指标采集、日志采集 | 这些**不在我方可交付范围**，我方无法单方面保证 |
| 2 | 先做 B 会引入「平台未就绪 ⇒ 交付受阻」的外部依赖 | **反向增加**交付风险，与「私有化交付持牌机构」的定位相悖 |
| 3 | B 的价值是「一个控制台管多个私有化系统」，这取决于客户是否已有平台 | 属商务事实，工程侧无法预判 |
| 4 | A 已经能独立满足「客户拿到包就能装、能验收」 | 先做 A 不损失任何已交付能力 |

## 3. 商务侧仍需确认的 3 问（只影响是否同时推 B）

| # | 问题 | 若答「是」我方动作 | 若答「否」我方动作 |
|---|---|---|---|
| Q1 | 客户是否**已有或指定**运维平台？（是否要求由一个控制台纳管交付物？） | 提供平台侧最小能力清单（§4），做联调实测 | 维持 A 现状，投断网机整链 / SBOM / 其余模块 jar 补齐 |
| Q2 | 客户环境是否允许**导入第三方镜像**（离线镜像仓库 / 允许 `docker load`）？ | 交付包按 `--with-images` 出镜像 tar | 只出 jar 裸进程路径（`--with-jars`） |
| Q3 | 交付**验收方式**是否要求「由平台下发」而不只是「由平台安装」？ | 联调纳入验收项（联调方案 §7 的 J1~J4） | 验收仍走离线整链（`offline-drill.sh`） |

> **这 3 问不改变工程默认**：无论怎么答，交付包形态不变，切换成本 ≈ 0。

## 4. 若走 B：平台侧最小能力清单（我方已就绪，可逐条核对）

| # | 平台侧需具备 | NexusChain 侧对应物 |
|---|---|---|
| 1 | 按 `images.lock` 导入/拉取镜像（离线 tar 或镜像仓库） | `images.lock`（19 条，含来源路径） |
| 2 | 安装 `charts/nexus-chain-<ver>.tgz` 并注入参数 | chart 包 + `dependencies.lock` + `.env.prod.example`（19 个强制变量） |
| 3 | 探活 | `GET /actuator/health`（sandbox 返回 503 是「下游指标缺失」，不是进程挂） |
| 4 | 指标采集 | `GET /actuator/prometheus`（**Bearer token**，无/错 token 一律 401） |
| 5 | 日志采集 | stdout（应用日志全走 stdout） |
| 6 | 任务下发（安装/体检/验收/升级/回滚） | `bash scripts/ops/nc-task.sh <action>`，回执=单行 JSON，退出码 0/1/2 |

## 5. 不可逾越的底线

**NexusChain 不得因为「平台不可用」而不能交付**：交付物自身必须能独立安装、独立自证、
独立跑端到端验收（`offline-install.md` §2.1 的 PASS 6 / FAIL 0 / SKIP 0 就是这条底线的证据）。
B 是**多一条路**，不是**换一条路**。
