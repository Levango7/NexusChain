## 一、逐项证据链

### 1️⃣ L2 ZK 证明系统——非真实 Groth16（确认）

**代码自述（三重证据互相印证）**：

| 证据 | 位置 | 内容 |
|---|---|---|
| 类头 Javadoc | `nexus-core/.../l2/zk/groth16/Groth16ProofSystem.java:21-25` | "由于 secp256k1 不支持双线性配对（真实 Groth16 验证所需），本实现采用 Schnorr 知识证明协议 + Fiat-Shamir 变换替代配对验证" |
| 与真实 Groth16 区别声明 | `Groth16ProofSystem.java:66-71` | "真实 Groth16 使用双线性配对 e(A,B)=e(α,β)·e(γ,pub)·e(δ,C)；本简化版用 Schnorr 协议替代配对验证" |
| prove 实现 | `Groth16ProofSystem.java:398-462` | Pedersen 承诺 + Fiat-Shamir 挑战 e=H(C,T,pub,circuitId) + 响应 z=t+e·d → 纯 Schnorr 结构 |
| verify 实现 | `Groth16ProofSystem.java:562-613` | 校验 Schnorr 等式 + R1CS 满足性证明（`verifyR1csSatisfactionProof`，629 行） |
| 状态根编码限制 | `Groth16ProofSystem.java:88-92` | "long[] 无法完整表达 256 位 bytes32 状态根"（ZK-P2-01 自认） |
| README 诚实声明 | `README.md:105-107` | "三重降级：halo2 (FROZEN) → Groth16 (声称) → Schnorr (实际)" |

**判定**：真实 Groth16 需要配对友好曲线（BN254/BLS12-381）+ R1CS 完备约束 + 可信设置。当前是 Schnorr 知识证明 + 简化 R1CS——**不具备真实 ZK 的通用电路安全属性**，仅可用于逻辑流程验证。

## 二、改进设计方案（逐项修复路径）

### 方案 A：L2 ZK 真实化（P0，最高优先级）

```
现状：Schnorr 替代（无配对）+ long[] witness + 简化 R1CS
目标：真实 Groth16 / Plonk
路径（按成本递增可选）：
  A1（2-4 周，推荐先行）：换 BN254/BLS12-381 配对曲线 + 完整 Groth16
     → 引入 arkworks/bn254 或 mclbn256，重写 Groth16ProofSystem 的
       pairing check e(A,B)=e(α,β)·e(γ,pub)·e(δ,C)
  A2（4-8 周）：接入 halo2（原 ADR-001 FROZEN 解冻）或 gnark，电路 DSL 化
  A3（并行）：witness 从 long[] 升级 BigInteger[]（解除 ZK-P2-01 编码限制）
验收：真实配对验证通过 + 完备约束（签名/nonce/gas 约束补全）+ ZK 安全属性审计
```

### 方案 B：MPC 分布式化（P0）

```
现状：可信协调器（单进程持有全部 n 方份额）
目标：真 t-of-n 分布式（n 方分进程，≤t-1 方被攻破不泄露私钥）
路径：
  B1（1-2 周）：修正文档——声明"已编译 + 可信协调器"，停止过度谦逊
  B2（4-8 周）：利用 server.rs 已有 with_party_id/会话身份绑定（MPC-P2-F5），
     部署为 3 独立进程 + mTLS 证书鉴权（gRPC mTLS 已实现）；
     集成测试从 #[ignore] 转为 CI 强制（Linux runner + openssl + protoc）
  B3（8-12 周）：份额跨进程隔离 + 门限容错验证（t-1 节点宕机仍可签名）
验收：3 节点 2-of-3 真实签名 E2E 通过（无单进程全份额路径）
```

### 方案 C：治理/退款/签名 P0 收尾（1-2 周）

```
C1：更新 README.md:82、:141 等过时声明（治理执行 P0 已修复）

C3：为退款 CAS 与签名阻断加并发压测用例（验证 EXECUTING 竞争）
```

### 方案 D：Spring Boot 升级（1-2 周）

```
D1：Boot 3.2.5 → 3.4.x（LTS 线，Spring Cloud 2024.0.x / SCA 2023.0.3.x 联动）
D2：升级后全量回归（4190 用例基线保持 0 失败）
D3：清理 core 遗留老库（json-lib 2.4 / json-simple 1.1.1 → Jackson，成本低收益高）
```

### 方案 E：sdk 测试稳定化（0.5 周）

## 四、最终判定

**NexusChain 是一个工程化水准高于同类项目的支付编排平台**：27.9 万行有序代码、494 测试文件 / 4190 用例全绿、5 条 CI 流水线、技术债有系统治理、诚实声明文化真实可信（README 未夸大——除 MPC"未编译"一处因构建产物存在而过时外，其余声明均与代码吻合）。

**交付前的决定性差距仅剩两项安全硬伤**：① L2 ZK 非真实（Schnorr 替代）；② MPC 可信协调器（单点全份额）。**按方案 A1 + B1/B2 并行推进，2-4 周可达到"可签 SLA 的 POC 试点"标准**；随后 Spring Boot 升级（D）+ 完整回归，即可进入商业化售卖窗口。

**建议优先级**：**A1（ZK 配对真实化）> B2（MPC 分布式 E2E）> C1（文档对齐）> D（Boot 升级）> E（sdk 稳定）**。前两项决定安全性质变，后三项决定交付信心。
