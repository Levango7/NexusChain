## 2. MPC 引擎审计

### 2.1 GG20 协议实现正确性

**审查文件**：`mpc-engine/src/gg20.rs`（567 行）

**实现分析**：

代码基于 ZenGo-X/KZen `multi-party-ecdsa` 0.8.1 crate，实现了完整的 GG20 门限 ECDSA 协议：

- **DKG 阶段**（`run_keygen`，行 73-166）：4 轮协议完整实现
  - Phase 1：各方生成 Paillier 密钥对并广播承诺（`Keys::create` + `phase1_broadcast_phase3_proof_of_correct_key_proof_of_correct_h1h2`）
  - Phase 2：Feldman VSS 分发私钥份额 + 验证承诺与 ZK 证明（`phase1_verify_com_phase3_verify_correct_key_verify_dlog_phase2_distribute`）
  - Phase 3：构造本地密钥对 + DLog 证明（`phase2_verify_vss_construct_keypair_phase3_pok_dlog`）
  - 全局验证：`Keys::verify_dlog_proofs_check_against_vss`

- **Sign 阶段**（`run_sign`，行 174-408）：7 轮协议完整实现
  - Phase 1：广播 g^gamma_i 承诺 + Paillier 加密 k_i
  - Phase 2：MtA 交换（MessageA / MessageB），计算 delta_i / sigma_i
  - Phase 3：重构 delta^{-1}，计算 T_i 并验证 Pedersen 证明
  - Phase 4：解承诺得到 R
  - Phase 5：PDL 证明验证
  - Phase 6：S_i 一致性证明验证
  - Phase 7：聚合签名 + 库内验证

- **独立验签**（`verify_signature`，行 411-455）：使用独立 `secp256k1` crate（非 GG20 内部 `verify`）验证签名，证明门限签名与单密钥 ECDSA 兼容。

**正确性结论**：GG20 协议数学实现正确，测试 `gg20_end_to_end_real_threshold_ecdsa`（t=1, n=3）端到端验证通过，包含负面用例（篡改消息验证失败）。

### 2.2 可信协调器模型的安全限制（诚实声明）

**审查文件**：`gg20.rs` 行 7-12、`dkg.rs` 行 5-12、`sign.rs` 行 5-9、`server.rs` 行 7-11

**实现现状**：

代码在所有模块顶部以「诚实声明」明确记录了部署模型限制：

> 本模块在单一进程内模拟全部 n 个参与方运行 GG20 协议，属于「可信协调器」模型——门限密码学的数学是真实的，但各方私钥份额暂驻留同一进程，而非分散在互不信任的独立节点上。

**安全影响**：

可信协调器模型**不满足门限密码学的核心安全属性**：

- **t-of-n 容错性失效**：门限 ECDSA 的安全保证是「t 方被攻破不泄露私钥」。当前所有 n 方份额驻留同一进程，进程被攻破即获得全部份额，等价于单点签名。
- **抗腐败模型退化**：从「至多 t 方腐败」退化为「至多 0 方腐败」（即不容许任何腐败）。
- **门限属性仅形式保留**：`threshold` 参数仅影响签名方数量，不影响密钥材料分布。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| MPC-P1-01 | **P1** | 可信协调器模型：全部 n 方私钥份额驻留同一进程内存 | 门限容错属性失效，进程被攻破即等价单点签名 |

**风险缓解**：代码已诚实声明此限制，且 `SignCache.partial_shares` 字段标注 `#[allow(dead_code)]` 注释「公开 API：分散式协调器演进时分发部分份额」，预留了演进路径。

### 2.3 密钥材料驻留内存的风险

**审查文件**：`gg20.rs` 行 35-47（`DkgSession`）、行 500-508（`SignCache`）；`server.rs` 行 31-34

**实现现状**：

```rust
pub struct MpcCryptoServiceImpl {
    pub sessions: Mutex<HashMap<String, DkgSession>>,
    pub sign_runs: Mutex<HashMap<String, SignCache>>,
}
```

`DkgSession` 含全部 n 方的：
- `party_keys: Vec<Keys>` — 各方 Paillier 密钥对（含私钥 `dk`）
- `shared_keys: Vec<SharedKeysSerde>` — 各方私钥份额 `x_i`
- `dlog_proofs: Vec<DLogProof>` — DLog 证明
- `ek_vec: Vec<EncryptionKey>` — Paillier 加密密钥
- `vss_scheme: VerifiableSS` — Feldman VSS 方案

**安全风险**：

- **无加密保护**：密钥材料以明文形式驻留 `HashMap`，进程内存 dump 攻击（如 `gcore` / `/proc/<pid>/mem`）可获取全部私钥份额。
- **无 zeroize**：Rust 中 `Scalar` / `EncryptionKey` 等类型未实现 `Zeroize` trait，内存释放后数据仍残留。
- **无 TEE 集成**：未使用 Intel SGX / AMD SEV 等机密计算技术保护密钥材料。
- **缓存无淘汰**：`sessions` 与 `sign_runs` 无 TTL、无容量上限、无 LRU 淘汰，长期运行将累积大量密钥材料。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| MPC-P1-02 | **P1** | 密钥材料明文驻留内存，无加密、无 zeroize、无 TEE 保护 | 内存 dump 攻击可获取全部私钥份额 |
| MPC-P2-01 | **P2** | DKG/Sign 缓存无 TTL、无容量上限、无淘汰策略 | 长期运行内存累积，DoS 风险 |

### 2.4 gRPC 传输安全（mTLS 配置）

**审查文件**：`mpc-engine/src/main.rs` 行 49-52；`GrpcMpcCryptoEngine.java` 行 91-118；`MpcTransportGrpcServer.java` 行 100-104；`GrpcMpcTransportStub.java` 行 176-186

**实现现状**：

- **Rust 引擎**（`main.rs`）：`tonic::transport::Server::builder().add_service(server).serve(bind)` — **未配置任何 TLS**，纯明文 gRPC 服务。
- **Java 客户端**（`GrpcMpcCryptoEngine`）：`@Value("${mpc.engine.use-plaintext:true}")` 默认 `true`，调用 `builder.usePlaintext()`。代码注释「生产环境应设为 false 并配置 mTLS（设计文档 §7.1 R10）」，但**无 mTLS 实现代码**，仅留有语义占位。
- **Java P2P server**（`MpcTransportGrpcServer`）：`ServerBuilder.forPort(port).addService(...)` — 默认明文，注释「生产环境应使用 SslContext 配置 mTLS」，但**无 SslContext 构造代码**。
- **Java P2P 客户端**（`GrpcMpcTransportStub`）：`if (usePlaintext) builder.usePlaintext()` — 同样无 mTLS 实现。

**安全风险**：

- **中间人攻击**：明文 gRPC 传输可被网络中间人窃听/篡改。MPC 协议消息（Paillier 密文、MtA 消息、部分签名）在传输中可被篡改，导致签名错误或密钥泄露。
- **认证缺失**：无客户端证书校验，任何能连接到 gRPC 端口的调用方均可调用 Dkg/Sign/Aggregate RPC。
- **配置默认不安全**：`use-plaintext` 默认 `true`，开发模式与生产模式默认值相同，运维需显式关闭。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| MPC-P0-01 | **P0** | Rust mpc-engine gRPC 服务端未配置 TLS，纯明文传输 | 中间人可窃听/篡改 MPC 协议消息 |
| MPC-P0-02 | **P0** | Java gRPC 客户端/服务端默认 `usePlaintext=true`，无 mTLS 实现代码 | 生产环境默认明文，认证缺失 |
| MPC-P1-03 | **P1** | gRPC 服务无认证/授权检查，任何连接方可调用 Dkg/Sign/Aggregate | 未授权调用方可触发密钥生成/签名 |

## 3. ZK 证明系统审计

### 3.1 Groth16 实现正确性

**审查文件**：`Groth16ProofSystem.java`（347 行）

**实现分析**：

代码声称实现 Groth16，但实际为 **Schnorr 知识证明 + Pedersen 承诺**，并非真实 Groth16：

- **setup**（行 90-160）：生成 Groth16 风格的 toxic waste (α, β, γ, δ) 和承诺点 G_i, H_i，但 toxic waste 保存在 `Groth16ProvingKey.ToxicWaste` 中未销毁。
- **prove**（行 170-230）：
  1. 验证 witness 满足 R1CS（prover 自检）
  2. 计算 witness 摘要 d = Σ w_i · (i+1) mod n
  3. Pedersen 承诺 C = d · G + r · H
  4. Schnorr 协议：T = t_d · G + t_r · H
  5. Fiat-Shamir 挑战 e = H(C, T, publicInput, circuitId)
  6. 响应 z_d = t_d + e · d, z_r = t_r + e · r
  7. 返回 (A=C, B=T, C=z_d·G+z_r·H)

- **verify**（行 240-282）：
  1. 重计算挑战 e
  2. 检查 Schnorr 等式：C_point == T + e · C
  3. **不验证 witness 满足 R1CS**

**正确性结论**：Schnorr 协议本身实现正确（满足完备性、零知识性、可靠性），但**这不是 Groth16**。

### 3.2 Schnorr 协议替代配对的安全影响

**核心安全缺陷**：

真实 Groth16 的验证等式为：
```
e(A, B) = e(α, β) · e(γ, pub) · e(δ, C)
```
该等式**同时验证**：(1) prover 知道 witness，(2) witness 满足 R1CS，(3) 公共输入正确。

当前实现的 Schnorr 验证等式：
```
C_point == T + e · C
```
仅验证 (1) prover 知道承诺的打开，**不验证** (2) witness 满足 R1CS，**不验证** (3) 公共输入与承诺的绑定。

**攻击路径**：

恶意 prover 可构造通过 Schnorr 验证但不满足 R1CS 的证明：
1. 任意选择 d, r，计算承诺 C = d · G + r · H
2. 执行 Schnorr 协议得到 (A, B, C)
3. verifier 验证 Schnorr 等式通过
4. 但 d 对应的 witness 不满足任何 R1CS 约束

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| ZK-P0-01 | **P0** | Schnorr 替代配对验证：verifier 不验证 witness 满足 R1CS | 恶意 prover 可伪造通过验证的证明，证明不保证状态转换合法性 |
| ZK-P0-02 | **P0** | toxic waste (α, β, γ, δ) 在 setup 后保留在 ProvingKey 中 | toxic waste 泄露可伪造任意证明（Groth16 安全前提是 toxic waste 销毁） |
| ZK-P1-01 | **P1** | 实现名为 Groth16 实为 Schnorr，双重降级（halo2 → Groth16 → Schnorr） | 误导下游使用者对安全属性的判断 |

### 3.3 R1CS 约束完备性

**审查文件**：`RollupStateTransitionCircuit.java`（223 行）

**实现现状**：

电路定义的 R1CS 约束（`buildR1cs`，行 127-171）：

- **C1**：`sumEffects = Σ txEffect_i`（线性累加约束）
- **C2**：`postStateRoot - preStateRoot = sumEffects`（状态守恒约束）
- **C3..C_{n+2}**：每笔交易的占位约束 `(txEffect_i) * (1) = (txEffect_i)`（**恒成立，无意义**）

**缺失的关键约束**：

真实 Rollup 状态转换电路应包含但当前缺失：
- 交易签名验证（每笔交易的 ECDSA 签名合法）
- Nonce 单调递增（防重放）
- Gas 余额检查与累计
- 状态根逐笔更新（Merkle Patricia Trie 转换）
- 交易格式与字段范围约束
- 合约执行 trace 约束（EVM 状态机）

**安全影响**：

当前电路仅证明「postStateRoot - preStateRoot = Σ txEffect_i」这一线性关系，**不证明任何交易合法性**。攻击者可构造任意 `txEffect_i` 使等式成立，从而「证明」非法状态转换。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| ZK-P0-03 | **P0** | R1CS 约束严重不完备：缺少签名验证、nonce、gas、状态根更新等约束 | 电路不证明交易合法性，可证明任意状态转换 |
| ZK-P1-02 | **P1** | 占位约束 `(txEffect_i) * 1 = txEffect_i` 恒成立，无意义 | 约束数量虚高，不提供任何安全保证 |

## 4. 治理执行审计

### 4.1 权限校验

**审查文件**：`GovernanceExecutionDispatcher.java`（213 行）

**实现现状**：

`GovernanceExecutionDispatcher` 监听 `ProposalStatusChangedEvent`，当状态为 `PASSED` 时分发执行：

```java
@EventListener
public void onProposalStatusChanged(ProposalStatusChangedEvent event) {
    if (event.getNewState() != ProposalState.PASSED) return;
    dispatch(event.getProposalId(), event.getProposal());
}
```

**安全风险**：

- **事件源无认证**：任何 Spring Bean 调用 `eventPublisher.publishEvent(new ProposalStatusChangedEvent(...))` 即可触发治理执行。无校验事件发布者是否为 `GovernanceService`。
- **提案状态信任**：dispatcher 信任 `proposal.getState() == PASSED`，但 `Proposal` 对象的状态字段可被任意修改（无不可变保护）。
- **手动分发无鉴权**：`dispatch(String proposalId)` 公开方法无调用方权限校验。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| GOV-P0-01 | **P0** | 事件源无认证：任意组件发布 `ProposalStatusChangedEvent` 即可触发治理执行 | 未授权方可触发软件升级/国库转账 |
| GOV-P1-01 | **P1** | `Proposal` 状态字段可变，无不可变保护 | 提案状态可被运行时篡改 |

### 4.2 审计日志完整性

**审查文件**：`GovernanceAuditLog.java`（189 行）

**实现现状**：

```java
private final Map<String, List<AuditRecord>> auditLogByProposal = new ConcurrentHashMap<>();
```

审计日志存储在进程内 `ConcurrentHashMap` + `CopyOnWriteArrayList`。

**安全风险**：

- **无持久化**：进程重启后全部审计记录丢失，违反治理审计的不可篡改与可追溯要求。
- **无防篡改**：内存中的 `AuditRecord` 可被同进程代码修改/删除（`clear()` 方法直接清空）。
- **无哈希链/签名**：审计记录之间无链式哈希或数字签名，无法检测篡改。
- **无外部审计存储**：注释提到「后续可接入持久化审计存储（如 Elasticsearch / 关系库审计表）」，但当前未实现。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| GOV-P0-02 | **P0** | 审计日志仅内存存储，无持久化、无防篡改 | 进程重启丢失，治理操作不可追溯 |
| GOV-P1-02 | **P1** | `clear()` 方法公开，可清空全部审计记录 | 内部威胁方可抹除审计轨迹 |

### 4.3 异常处理

**审查文件**：`SoftwareUpgradeExecutor.java`、`TreasurySpendExecutor.java`、`GovernanceExecutionDispatcher.java`

**实现现状**：

- 执行器内部 `catch (Exception e)` 捕获所有异常，回写 `EXECUTION_FAILED` 状态。
- 调度器有兜底 `catch (Exception e)` 防止调度器崩溃。
- 异常信息 `e.getMessage()` 直接放入 `executionResult` 和审计日志。

**安全风险**：

- **异常信息泄露**：`e.getMessage()` 可能含敏感信息（如数据库连接串、私钥路径），直接放入 `executionResult`（持久化到提案）和审计日志。
- **fail-open 风险**：`dispatch` 方法在异常时返回 `false`，但 `@Async` 事件监听器的异常被 Spring 吞掉，调用方无法感知失败。
- **状态不一致**：执行器先 `proposal.setState(EXECUTION_FAILED)` 再发事件，若事件发布失败，提案状态已变更但下游未通知。

**发现**：

| ID | 级别 | 发现 | 影响 |
|----|------|------|------|
| GOV-P2-01 | **P2** | 异常信息直接放入 executionResult 和审计日志 | 可能泄露敏感信息 |
| GOV-P2-02 | **P2** | `@Async` 监听器异常被 Spring 吞掉，调用方无感知 | fail-open 风险 |

### 4.4 治理执行其他发现

**审查文件**：`TreasurySpendExecutor.java` 行 196-200；`SoftwareUpgradeExecutor.java` 行 175-179

| ID | 级别 | 发现 | 影响 | 位置 |
|----|------|------|------|------|
| GOV-P0-03 | **P0** | `TreasurySpendExecutor.generateTxHash` 用 `hashCode()` 生成转账哈希 | 32 位哈希碰撞概率高，转账可被伪造/混淆 | 行 196-200 |
