# LGPL 组件声明与重链接方案（交付用）

> 建立于 2026-10-12。**本文是技术口径与材料清单，不是法律意见**：最终表述需法务/客户合规确认。
> 内部事实台账（含逐条文件行号证据）在 [`docs/licensing.md`](licensing.md) §5，本文是它的**对外版**。

## 1. 事实（可复核）

| 项 | 内容 | 证据 |
|---|---|---|
| 涉及组件 | `rug 1.30.0`、`gmp-mpfr-sys 1.7.1`（底层 GMP/MPFR，**LGPL-3.0-or-later**） | `mpc-engine/Cargo.lock` 逐字锁定 |
| 引入路径 | `cggmp21` → `paillier-zk` → `fast-paillier 0.1.1` → `rug`/`gmp-mpfr-sys`（**传递依赖，非直接选用**） | `mpc-engine/Cargo.toml:28` 注释 + `Cargo.lock` 依赖块 |
| 影响范围 | **仅 `mpc-engine`（Rust 门限签名引擎）**；Java 服务与 explorer 的依赖树无 LGPL | `docs/licensing.md` §5 + CI 依赖许可扫描（报告制） |
| cggmp21 自身 | MIT OR Apache-2.0（宽松） | 同上 |
| 历史变更 | 2026-10-08 GG20 退役后，此前 5 个 **GPL-3.0 系** crate 已全部移除（GPL 比 LGPL 严格，已解） | `docs/plan/PLAN-001-gg20-retirement.md` |

**一句话**：我们以目标代码形式分发、且 Rust 默认**静态链接**了该 LGPL 库
（`mpc-engine` 产物内嵌其代码），因此触发 LGPL-3.0 §4 的"可重新链接"义务。

## 2. 义务（LGPL-3.0 §4，分发目标代码时）

以目标代码形式分发含 LGPL 组件的作品时，须满足以下**之一**（原文 §4(d)）：

- **(0)** 随附"最小对应源码（Minimal Corresponding Source）"**与应用侧可重链接形式**（目标文件
  或适配的共享库机制），使用户能修改该 LGPL 组件并重新链接出可运行的组合作品；
- **(1)** 使用"适配的共享库机制"（即把 LGPL 组件以**动态库**形式链接）——用户替换该动态库即可。

另需（§4(e) 组合作品）：显著声明其中含 LGPL 组件及其许可。

## 3. 三条可选交付姿态（推荐 A，最省事；B 最干净但要改构建）

| 姿态 | 做法 | 交付物料 | 工程量 |
|---|---|---|---|
| **A. 静态链接 + 材料随附（推荐）** | 保持现状（Rust 静态链接），向客户提供：① LGPL 组件的**完整对应源码**（含我们的任何修改——实际为零修改）；② **应用侧目标文件**（`mpc-engine` 的 `.o`/`.rlib`）或**书面向客户承诺提供**；③ 重链接步骤说明；④ 组合作品声明 | `THIRD-PARTY-LGPL-NOTICE.md`（本目录可生成）+ 源码包（crates.io 上游 + 校验和）+ 目标文件包 | **低**（打包 + 文档） |
| **B. 动态链接（§4(d)(1)）** | 把 `rug`/`gmp-mpfr-sys` 编成动态库随镜像分发（`RUSTFLAGS`/`cargo` 配置 + `ldd` 校验），用户可替换 | 声明 + `.so` + 替换说明 | **中**（构建与镜像改动 + 验证 glibc/ABI 兼容） |
| **C. 不分发** | 私有化交付若为**单一持证主体内部自用、不再对外分发**，LGPL 义务不触发 | 与客户书面确认"不再分发"的条款 | **零**（纯商务） |

> 我们的建议顺序：**A**（对所有分发场景通用、改动最小）→ 若客户合规明确要求"可替换动态库"
> 则做 **B** → 若交付形态确定是单主体自用则走 **C** 以简化。

## 4. 走 A 时的物料清单（可执行）

1. **源码包**（对应源码，§1 中两个 crate 的版本必须与镜像内实际链接的一致）：
   - `rug 1.30.0`：`https://crates.io/api/v1/crates/rug/1.30.0/download`
   - `gmp-mpfr-sys 1.7.1`：`https://crates.io/api/v1/crates/gmp-mpfr-sys/1.7.1/download`
   - 其捆绑/链接的 GMP、MPFR 上游源码（`gmp-mpfr-sys` 自带构建脚本会下载；须一并提供同一版本）
   - 校验：以 `Cargo.lock` 的 `checksum` 字段为准（逐字比对，不靠人工记忆版本号）
2. **应用侧可重链接形式**：`mpc-engine` 的静态库/目标文件（随版本一起打包），
   并给出重链接命令（`cargo build` + 替换 `.so`/重新链接的步骤）。
3. **声明文本**：镜像内 `THIRD-PARTY-NOTICE` 与本项目 `NOTICE` 同步一段"含 LGPL-3.0+ 组件
   （rug/gmp-mpfr-sys），其完整源码与重链接方式见交付包 `<路径>`"。
4. **交付包结构建议**：`licenses/LGPL/`（源码包 + 校验和 + 重链接说明 + 声明）。

## 5. 边界与不做的事（诚实声明）

- **不做**：不在本文件里下"许可已完全合规"的结论——LGPL 义务的满足方式（尤其"目标文件"是否
  达到 §4(d)(0) 的"适用形式"）属法律判断，需法务确认。
- **不做**：不把 `rug`/`gmp-mpfr-sys` 换掉——`cggmp21` 是唯一密码学路径，换成别的 bignum 实现
  等于重写门限签名底层（数周级、且引入新风险）。
- **待办**：① 物料打包脚本（本清单的第 1、2 步自动化）；② 若走 B，需一次"替换 `.so` 后仍能
  完成签名"的实测；③ 客户合规口径确认（走 A/B/C 哪条）。
