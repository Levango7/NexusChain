> **版本**：1.0  
> **生效日期**：2026-08-09  
> **适用范围**：NexusChain 全量代码库与运行时环境  
> **关联文档**：[v2.0.0-roadmap.md](./v2.0.0-roadmap.md) · [security-scan.yml](../.github/workflows/security-scan.yml)

## 第1章 概述

### 1.1 目的

本文档定义 NexusChain 项目安全漏洞发现的响应与修复时限（SLA），确保安全风险在规定时间内得到处置，避免漏洞长期暴露。SLA 与 CI/CD 安全扫描流水线（`.github/workflows/security-scan.yml`）联动，高危发现自动创建 GitHub Issue 并标注截止时间。

### 1.2 适用场景

- CI/CD 流水线自动扫描发现（Trivy / SpotBugs+FindSecBugs / OWASP ZAP / OWASP Dependency-Check）
- 人工安全审计发现（内部审计 / 第三方渗透测试）
- 外部漏洞报告（安全研究员提交 / CVE 公告匹配）

### 1.3 术语

| 术语 | 定义 |
|------|------|
| **SLA** | Service Level Agreement，服务等级协议，此处指漏洞修复时限承诺 |
| **TTL** | Time To Live，漏洞从发现到修复的存活时间 |
| **MTTR** | Mean Time To Remediate，平均修复时间 |
| **CVSS** | Common Vulnerability Scoring System，通用漏洞评分系统（v3.1） |

## 第2章 严重性分级与 SLA

### 2.1 分级标准

漏洞严重性基于 CVSS v3.1 评分与业务影响综合判定：

| 优先级 | 标签 | CVSS 评分 | 严重性 | 业务影响 |
|--------|------|-----------|--------|---------|
| **P0** | `P0` | 9.0 – 10.0 | CRITICAL | 可被远程利用导致 RCE / 数据泄露 / 资金损失 |
| **P1** | `P1` | 7.0 – 8.9 | HIGH | 可导致权限提升 / 敏感信息泄露 / 服务中断 |
| **P2** | `P2` | 4.0 – 6.9 | MEDIUM | 需特定条件触发 / 影响有限 |
| **P3** | `P3` | 0.1 – 3.9 | LOW | 信息性发现 / 最佳实践偏离 |

### 2.2 SLA 时限

表：安全发现 SLA 时限

| 优先级 | 严重性 | 响应时限 | 修复时限 | 验证时限 | 总 TTL |
|--------|--------|---------|---------|---------|--------|
| **P0** | CRITICAL | 1 小时 | **24 小时** | 4 小时 | 28 小时 |
| **P1** | HIGH | 4 小时 | **7 天** | 1 天 | 8 天 |
| **P2** | MEDIUM | 1 天 | **30 天** | 2 天 | 32 天 |
| **P3** | LOW | 3 天 | 90 天 | — | 93 天 |

> **响应**：确认漏洞有效性并分配负责人  
> **修复**：提交修复 PR 并通过 CI 验证  
> **验证**：安全扫描确认漏洞已消除

### 2.3 特殊情形

- **0-day 漏洞**（无官方修复版本）：P0 立即启动应急响应，24h 内提供缓解方案（WAF 规则 / 配置加固 / 功能禁用）
- **依赖链漏洞**（传递依赖）：SLA 取依赖根包的优先级，修复时限放宽 1.5 倍（需协调上游升级）
- **测试代码漏洞**：SLA 降一级（测试代码不进入生产攻击面）
- **已缓解漏洞**（WAF / 网络隔离已阻断攻击路径）：SLA 降一级，但需在 issue 中记录缓解措施

## 第3章 响应流程

### 3.1 自动化流程（CI/CD 触发）

图：安全发现自动化响应流程图

```
CI 扫描发现漏洞
      │
      ▼
┌─────────────────────┐
│ trivy-to-issues.py  │  解析报告，提取 CRITICAL/HIGH
│ 去重检查            │  按 CVE+包名指纹去重
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 创建 GitHub Issue   │  标注 P0/P1/P2 label
│ 填充 SLA 截止时间   │  @-mention 安全负责人
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ Dependabot 匹配     │  若有官方修复版本
│ 自动创建升级 PR     │  关联 issue
└─────────┬───────────┘
          │
          ▼
    人工审查 + 合并
```

### 3.2 人工响应流程

#### 3.2.1 P0（CRITICAL）— 应急响应

1. **T+0h**：发现漏洞，自动创建 Issue + 通知安全负责人
2. **T+1h**：安全负责人确认漏洞，组建应急小组
3. **T+4h**：制定修复 / 缓解方案
4. **T+24h**：提交修复 PR，通过 CI 安全扫描
5. **T+28h**：修复部署至生产环境，验证漏洞已消除

#### 3.2.2 P1（HIGH）— 标准响应

1. **T+0d**：发现漏洞，自动创建 Issue
2. **T+1d**：分配负责人，评估影响范围
3. **T+7d**：提交修复 PR，通过 CI 验证
4. **T+8d**：修复合并，关闭 Issue

#### 3.2.3 P2（MEDIUM）— 常规响应

1. **T+0d**：发现漏洞，记录至 backlog
2. **T+30d**：在下一个迭代窗口修复
3. **T+32d**：验证并关闭

### 3.3 升级路径

| 触发条件 | 升级动作 |
|---------|---------|
| P0 超过 24h 未修复 | 升级至 CTO + 安全委员会 |
| P1 超过 7d 未修复 | 升级至技术负责人 |
| P2 超过 30d 未修复 | 升级至项目经理，纳入下迭代强制项 |
| 同一漏洞 3 次复发 | 升级至架构审查，根因分析 |

## 第4章 CI/CD 集成

### 4.1 扫描器与 SLA 映射

| 扫描器 | 类型 | 覆盖严重性 | 对应 SLA |
|--------|------|-----------|---------|
| Trivy fs / image | SCA | CRITICAL → LOW | P0 – P3 |
| OWASP Dependency-Check | SCA | CRITICAL → LOW | P0 – P3 |
| SpotBugs + FindSecBugs | SAST | HIGH → LOW | P1 – P3 |
| OWASP ZAP Baseline | DAST | HIGH → LOW | P1 – P3 |
| CycloneDX SBOM | SCA | — | 审计基线 |

### 4.2 自动化触发条件

- **push 到 master**：全量扫描（SAST + SCA）
- **每周一 03:00 UTC**：定时全量扫描（SAST + DAST + SCA + SBOM）
- **手动触发**：`workflow_dispatch`，可选扫描范围
- **Dependabot**：每周检查依赖更新，自动创建升级 PR

### 4.3 Issue 自动创建

由 `scripts/security/trivy-to-issues.py` 实现：

- 解析 Trivy JSON 报告
- 按 `CVE + 包名 + 目标` 指纹去重
- 对 HIGH 及以上漏洞创建 GitHub Issue
- Issue body 包含：漏洞详情、CVSS 评分、修复版本、SLA 截止时间
- 自动打标签：`security-triage`、`security`、`P0`/`P1`/`P2`、`automated`

### 4.4 阻断策略

- **CRITICAL 漏洞**：CI 流水线 `exit-code: 1`，阻断合并
- **HIGH 漏洞**：创建 Issue + PR comment 警告，不阻断（可配置）
- **MEDIUM/LOW**：仅记录，不阻断

## 第5章 度量与报告

### 5.1 关键指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| **MTTR-P0** | P0 漏洞平均修复时间 | < 24h |
| **MTTR-P1** | P1 漏洞平均修复时间 | < 7d |
| **SLA 达成率** | 在 SLA 内修复的漏洞占比 | > 95% |
| **漏洞密度** | 每千行代码的漏洞数 | 持续下降 |
| **重复率** | 同一漏洞复发次数 | < 5% |

### 5.2 报告频率

- **周报**：每周一随定时扫描生成，包含本周新增 / 修复 / 待处理漏洞
- **月报**：SLA 达成率、MTTR 趋势、Top 10 风险包
- **事件报告**：P0 漏洞修复后 48h 内出具事后报告

### 5.3 审计基线

CycloneDX SBOM（`sbom-cyclonedx.json`）作为依赖审计基线，每次扫描产出并归档，用于：

- 供应链合规审计（SBOM 比对）
- 漏洞影响范围分析（哪些产品受某 CVE 影响）
- 许可证合规检查

## 第6章 责任分配

### 6.1 角色与职责

| 角色 | 职责 |
|------|------|
| **安全负责人** | SLA 监督、P0 应急响应指挥、扫描策略维护 |
| **模块维护者** | 所属模块漏洞修复执行、PR 审查 |
| **DevOps** | CI/CD 流水线维护、扫描器配置、SBOM 归档 |
| **架构师** | 重复漏洞根因分析、架构级安全改进 |

### 6.2 问责机制

- SLA 超时未修复：自动在 Issue 中 @-mention 上一级负责人
- 连续 2 周 SLA 达成率 < 80%：触发安全复盘会议
- P0 漏洞超时：列入项目风险登记册，向管理层报告
